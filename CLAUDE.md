## Ce projet en une phrase

Une application de productivité mobile-first de style RPG/Arcade 16-bits où chaque tâche créée soigne le Boss de la journée (+20 HP) et chaque tâche complétée lui inflige des dégâts, offrant une gratification immédiate pour vaincre la procrastination.

## Conventions — non négociables

### Langue d'échange
Toute communication avec l'utilisateur se fait en français, sans exception. Les termes techniques, noms d'API, de librairies, de variables, de commandes et le vocabulaire spécifique (ex: "commit", "fetch", "hook", "state") restent en anglais quand c'est l'usage naturel du domaine.

### Changelog (`CHANGELOG.md`)
Toute PR qui livre une feature (produit ou technique) ajoute sa ligne sous `## [Unreleased]` de `CHANGELOG.md`, dans le même commit que l'implémentation — jamais après coup. Format des versions : `XX.YY.ZZ` (Majeure.Mineure.Fix), aligné sur les releases GitHub. À chaque release GitHub effective, le contenu d'`[Unreleased]` est basculé dans une nouvelle section versionnée et datée.

### Documentation utilisateur (Le Guide — issue #68)
Avant de pousser une PR, **vérifier systématiquement si elle nécessite une doc utilisateur** et, le cas échéant, la produire **dans la même PR** :
- **Nouvelle feature visible par l'utilisateur** (écran, mécanique, règle de jeu) → **créer un nouvel article** dans la base Notion « Guide Dodojo » (catégorie appropriée parmi `ORDRE_SECTIONS`, `Statut = Publié`, `Slug` en minuscules/tirets, stable une fois publié — c'est l'URL `/guide/<slug>`).
- **Changement d'un comportement déjà documenté** (barème, rituels, streaks, or, combos, roster…) → **mettre à jour l'article Notion existant** (même `Slug`, ne jamais le renommer une fois publié — casserait les deep-links `StreakBadge`/Le Vestiaire/liens externes).
- **Source = Notion**, base « Guide Dodojo » : éditer/ajouter la page, `Statut = Publié`, puis `npm run pull:guide` pour régénérer `content/guide/<slug>.md` + `content/guide/index.json` (committés dans la PR). Si Notion n'est pas accessible (`NOTION_TOKEN` absent), éditer directement les fichiers `content/guide/<slug>.md`/`index.json` en respectant le schéma (`lib/guide.ts`), en **gardant les `Slug` stables**.
- **Uniquement si pertinent** : une PR purement technique/refactor/infra (sans impact sur ce que voit ou comprend l'utilisateur) n'exige **pas** de doc utilisateur — ne pas en inventer.

### Commits (Conventional Commits)
Format strict : `type: description courte`
- `feat:` Nouvelle fonctionnalité (ex: `feat: add screen shake animation on damage`)
- `fix:` Correction de bug (ex: `fix: prevent negative gold balance`)
- `chore:` Tâches de maintenance (ex: `chore: setup vitest config`)
- `docs:` Documentation technique uniquement.

### Workflow Git
- `main` est protégée. Aucun commit direct. Déploiement automatique sur Vercel.
- Une branche par fonctionnalité : `feat/us-XX-nom-feature`.
- **Zéro merge si la CI est rouge.** Tous les tests Vitest et l'application doivent build sans erreur.
- **Zéro PR poussée sur GitHub tant que les tests (Vitest + Playwright e2e) n'ont pas été passés en local.** Une fois la CI en place, elle vient en double sécurité, pas en remplacement de cette vérification locale.

## Règles de code

1. **TypeScript Strict :** Interdiction d'utiliser `any`. Tout type doit être explicitement déclaré (notamment les états de tâches et profils).
2. **Logique isolée dans `lib/` :** Tout algorithme de calcul de jeu (formule d'XP, calcul dynamique des HP maximum du Boss) doit résider dans `lib/game-engine.ts` pour être testé sans dépendances de rendu UI.
3. **Gestion des 3 états UI :** Tout écran (Arène, Le Vestiaire) doit obligatoirement implémenter un état de chargement (Loading), un état d'erreur (Error), et un état vide (Empty - ex: quand le Boss est K.O.).
4. **Pas de suppression destructive :** Les tâches ne doivent jamais être supprimées via un `DELETE` SQL. Utiliser exclusivement la colonne `is_abandoned` ou `is_completed` pour maintenir l'historique et la jauge du Boss (RG-04).

## Pièges et décisions non-évidentes

**Décalage horaire et Étanchéité du jour** — Le "jour" du jeu est le **jour local** de l'utilisateur, pas l'UTC. Il est calculé via `dayKey(date, timezone)` (`lib/game-engine.ts`) à partir de la colonne `profiles.timezone` (IANA, captée à l'onboarding via `Intl`). Toutes les requêtes/écritures `day_date` (server actions, `app/page.tsx`) passent par ce jour local. Ceci corrige le bug UTC de l'ancien `todayIso()` (à 01h à Paris on était encore "hier" en UTC) et le cas voyage/changement de fuseau. Le Boss est calculé uniquement sur les tâches du jour local courant (RG-03) ; les restes d'un jour local passé passent par Le Réveil (US-08, processus bloquant) avant toute nouvelle action.

**`deadlineIso` (US-05) : l'offset DST doit être recalculé au point fixe, pas probé une seule fois** — `deadlineIso(dayDate, timeHHMM, timezone)` convertit une heure locale saisie (`<input type="time">`) en ISO UTC. Une première version calculait l'offset du fuseau une seule fois, à l'instant "naïf" (HH:MM interprété directement comme UTC) — correct la plupart du temps, mais faux pour une heure locale valide **avant** une transition DST si l'instant naïf tombe **après** celle-ci : ex. `deadlineIso("2026-03-29", "01:30", "Europe/Paris")` (jour de passage à l'heure d'été, transition à 01h00 UTC) probait l'offset à +2 (post-transition) au lieu de +1 (pré-transition, l'heure réellement demandée), et renvoyait un horodatage décalé d'1h sans erreur ni crash — corruption silencieuse, y compris au round-trip via `localTimeFromIso`. Le correctif recalcule l'offset **à l'instant candidat obtenu**, pas seulement à l'instant naïf de départ (itération à point fixe, 2 passes suffisent pour tout delta DST réel) ; no-op pour toute date loin d'une transition (offset stable → une seule itération change rien).

**Pas de policy DELETE en RLS** — Les tables `profiles` et `tasks` n'ont volontairement aucune policy Supabase RLS pour `DELETE`. Ceci applique RG-04 au niveau base de données, en plus de la convention côté application (colonnes `is_abandoned` / `is_completed`).

**Pas de trigger d'auto-création de profil** — Aucun trigger sur `auth.users` ne crée automatiquement une ligne `profiles` à l'inscription. Le pseudo doit être défini explicitement par l'utilisateur (voir tone of voice : pas de fallback générique type "Héros"), donc la création de la ligne `profiles` fait partie du flow d'onboarding applicatif (US-14), pas de la migration SQL.

**Jauge de HP du Héros — dette soldée par Le Réveil (US-08) + pool pondéré (US-05)** — La jauge de HP du Héros (`calculateHeroHp` dans `lib/game-engine.ts`) n'est plus purement décorative. **Depuis US-05, le pool accepte un poids par tâche** (`HeroHpPenaltyTask`, champ `weight`) au lieu d'un poids fixe -20 pour toute la liste : une tâche en retard reportée d'un jour précédent (`overdueHpPenalties`) pèse -20 HP, une deadline horaire ratée du jour courant et non résolue (`deadlineHpPenalties` + `missedDeadlineTasks`) pèse -10 HP — les deux pools se combinent dans un seul appel à `calculateHeroHp`, plancher à 0. Le Réveil (`components/combat/WakeUpRitual.tsx`, US-08) traite les restes au démarrage via un overlay **bloquant** : Terminé / Reporter / Annihiler (+ actions groupées). Résoudre les restes (ou cocher/abandonner une tâche à deadline ratée) fait remonter la jauge instantanément (fonction pure recalculée à chaque rendu). La jauge ne peut donc plus rester à 0 indéfiniment sans action proposée. Voir le spec unifié `docs/superpowers/specs/2026-07-20-cycle-journee-design.md` et `docs/superpowers/specs/2026-07-22-us05-deadlines-design.md`.

**Cycle de la Journée & table `day_results`** — Les deux bornes du jour sont Le Réveil (US-08, ouverture, traitement des restes) et « Terminer la journée » (US-07, ex-"Obi-Wan", clôture cérémonielle non-bloquante). La table `day_results` (une ligne par `(user_id, day_date)`, contrainte unique) enregistre l'issue du jour (`victory` / `retreat` / `defeat`), les dégâts, l'XP, etc. — fondation du Tableau de Chasse (US-10), des Streaks (US-12) et du partage (US-20). Écriture **idempotente** (upsert, chiffres recalculés depuis les tâches, jamais accumulés) via `app/actions/day.ts` (`closeDay` à la clôture, `backfillMissedDays` en fin de Réveil pour l'historique sans trous). **Aucune policy DELETE** sur `day_results` (RG-04). "Annihiler" un reste = `is_abandoned = true`, jamais un DELETE.

**Profondeur des sous-tâches (RG-01) appliquée uniquement côté applicatif** — La colonne `parent_id` de `tasks` n'a aucune contrainte SQL (check/trigger) limitant la profondeur à 2 niveaux. La garde repose entièrement sur `isNestableParent`/`planReorder` (`lib/game-engine.ts`), revérifiés à la fois côté UI (bouton "+" absent sur une sous-tâche, `planReorder` refuse d'imbriquer une tâche qui a déjà des enfants) et côté server action (`reorderSiblings` dans `app/actions/tasks.ts`). Dette assumée pour le Sprint 1 : une action serveur appelée directement (hors UI) reste la seule ligne de défense, pas de filet base de données.

**Web Speech API : geste utilisateur direct obligatoire** — `SpeechRecognition.start()` (`hooks/useSpeechToText.ts`) doit être appelée de façon synchrone dans le handler `onClick` du bouton micro, sans détour asynchrone avant l'appel. Safari/iOS rejette silencieusement l'activation du micro si `.start()` n'est pas directement dans la pile d'un geste utilisateur. La détection de support navigateur (`SpeechRecognition` absent de `lib.dom.d.ts`, typé dans `types/speech-recognition.d.ts`) passe par `useSyncExternalStore` avec un snapshot serveur toujours `false`, pour éviter un mismatch d'hydratation Next.js entre le rendu serveur (pas de `window`) et le rendu client.

**E2E Playwright : exécution en série + serveur de production obligatoires** — `playwright.config.ts` force `fullyParallel: false` / `workers: 1` et démarre un serveur **prod** (`npm run build && npm run start`), pas `next dev`. Deux raisons cumulées, diagnostiquées en reproduisant le bug (9/9 vert en série, 6-8/9 KO dès 4 workers) : (1) tous les tests partagent l'unique compte e2e fixe (ADR-04), donc en parallèle ils mutent le même état (tâches, boss du jour) et se marchent dessus (contrôles restés `disabled`, redirections manquées) ; (2) `next dev` compile les routes à la demande, et sous parallélisme tous les workers déclenchent cette compilation en même temps, saturent le CPU et font dépasser le timeout de navigation. Ne pas revenir à `fullyParallel` sans d'abord isoler un compte Supabase par worker. Port surchargeable via `E2E_PORT` pour cohabiter avec un `next dev` local sur `:3000`.

**dnd-kit : `autoScroll` par défaut fausse la détection de collision sur les gestes fins** — `DndContext` a `autoScroll={false}` explicitement. Avec l'auto-scroll par défaut de dnd-kit activé, un drag qui approche le bord de la zone scrollable déclenche un scroll automatique **pendant** le geste ; les coordonnées absolues utilisées pour décider moitié haute/moitié basse d'une ligne (`isTopHalfDrop` dans `Arena.tsx`) se retrouvent décalées d'autant, et le geste "réordonner avant" peut basculer silencieusement en "imbriquer". Bug reproduit et diagnostiqué en e2e (Playwright) : la logique pure (`planReorder`, testée en Vitest) était correcte, seule la position live du pointeur dérivait pendant le drag. Si l'auto-scroll doit revenir un jour (listes très longues), il faudra recalculer la géométrie à partir d'un événement `onDragMove` en direct plutôt que d'une capture figée avant le drag.

**Économie d'or dérivée & Marché Noir de héros (US-18)** — L'or n'est jamais accumulé : `gold` = `SUM(day_results.gold_earned) − SUM(unlocked_heroes.price_paid)` (`goldBalance`, `lib/game-engine.ts`). `gold_earned` est écrit à la clôture (`closeDay`) et au backfill (traité **chronologiquement** pour un bonus streak correct) via `computeGoldEarned` (base par issue + part dégâts + bonus streak cappé). `profiles.gold` n'est qu'un **cache**. Le Marché Noir vend des **héros** (et non des skins de Boss — BDD d'origine révisée) : catalogue **statique** `lib/heroes.ts` (pas de table admin), rendu idle via `components/combat/IdleSprite` (frames PNG `/sprites/mc/<slug>/idle/frameNNNN.png`, index base 0 sur 4 chiffres). Possession dans `unlocked_heroes` (unique `(user_id, hero_id)`, **aucune policy DELETE**, RG-04, achat idempotent). `fire_knight` possédé d'office sans ligne (`isHeroOwned`). `profiles.equipped_hero_id` = héros affiché dans l'Arène (`VersusScene`, câblé via `Arena`). Skins/tenues (recolors) = US future ; nav = **hub Le Vestiaire** (Tableau de Chasse/Marché Noir via Le Vestiaire).

**Streaks à budget de jokers hebdo (US-12)** — La série (`currentStreak`, `lib/game-engine.ts`) compte les victoires consécutives mais **tolère jusqu'à 2 non-victoires (retreat/defeat/trou) par semaine ISO** (lundi→dimanche, dérivée du `day_date` local via `weekKey`) ; la 3e casse. Retourne `{ length, jokersUsedThisWeek, atRisk }`. **Changement de sémantique** : un trou isolé n'est plus une rupture (joker toléré). Dérivée de `day_results` (source unique) ; `profiles.streak_days`/`best_streak`/`current_title` sont des **caches** rafraîchis à la clôture (`closeDay`) et au backfill. Titres de jalon (`titleForStreak` : 7/30/100 → Calme/Silence/Esprit Vide) — écrasent `current_title` (provisoire, à fusionner avec d'éventuels titres de niveau). Compteur + alerte « en danger » au Vestiaire (`StreakBadge`), flammes à la victoire à la clôture (US-07 = « Terminer la journée »).

**Onboarding & économie du starter (US-29)** — Tunnel : `/welcome` (signup **client-side**, même patron que `/login` — jamais de server action pour l'auth, sinon le cookie de session ne se propage pas ; **« Confirm email » doit être OFF** côté Supabase) → `/onboarding` (pseudo → avatar) → Arène avec coach. Entrée non-auth : `/` redirige vers `/welcome` (les autres routes protégées gardent `/login`). **Changement d'économie** : `isHeroOwned(id, ownedIds)` ne renvoie **plus** `true` d'office pour le défaut — possession strictement via `unlocked_heroes`. Le starter choisi est offert (ligne `price_paid=0`) à `createProfile` ; `fire_knight` a désormais un prix non nul (sinon gratuit au Marché Noir). Migration de seed pour les profils existants + fixture e2e (`resetShopState` grante `fire_knight`). Coach du 1er combat (`ArenaCoach`, piloté par `profiles.has_seen_tutorial`) : étape « add » (suggestion « Prendre en main Dodojo ») → « strike » → `markTutorialSeen()` une fois (garde `useRef`) ; bouton « Passer » ; punchline « Premier sang » sur `PerfectOverlay` quand le KO tombe coach actif. e2e onboarding = compte dédié recréé à chaque run (`resetOnboardingUser`, creds `.env.local`).

**Le Guide — articles Notion multi-pages, sync auto au build (issue #68)** — Le guide est **statique** : `content/guide/<slug>.md` + `content/guide/index.json` (committés) rendus par `app/guide/page.tsx` (sommaire par catégorie) et `app/guide/[slug]/page.tsx` (article, SSG via `generateStaticParams`, `dynamicParams = false` — un slug hors du set résolu au build 404 au niveau routage, jamais de rendu à la demande ; sans ça, `notFound()` seul renvoie un fallback statique caché en HTTP 200, cf. header `x-nextjs-prerender: 1`). Source de vérité = base Notion **« Guide Dodojo »** (pas une simple page), filtrée sur `Statut = Publié`. **Aucune dépendance SDK Notion** — `scripts/pull-guide.mjs` interroge l'API REST Notion en `fetch` brut (`NOTION_TOKEN` seul requis ; `NOTION_DATABASE_ID` a un défaut hardcodé dans le script, override optionnel). Sync **automatique** via le hook `prebuild` de `package.json`, **tolérant** : token absent ou panne réseau ⇒ contenu committé conservé, le build ne casse jamais (`npm run pull:guide` pour un pull manuel strict). Rendu Markdown via `react-markdown` + `remark-gfm` (`components/guide/ArticleMarkdown.tsx`), pas de `rehype-raw` (le script ne produit que du Markdown pur). Slugs = anciens `section.id` conservés pour la continuité des deep-links : `StreakBadge` → `/guide/streak`, lien Marché Noir (Le Vestiaire) → `/guide/or`. Accès : Le Vestiaire + « ? » dans l'Arène (inchangé, pointe vers `/guide`).

**Roster de Boss & décors dynamiques** — Le boss (et son décor) du jour ne sont plus codés en dur. Catalogues **purs** : `lib/bosses.ts` (12 boss ; chaque boss porte `idleFrameCount`, `backgroundThemes` = thèmes de décor **cohérents avec son lore**, et `flip` = miroir horizontal car le boss est à droite et doit regarder le héros) + `lib/backgrounds.ts` (16 variantes sur 7 **thèmes** ; chaque décor a un champ `theme`). Le décor du jour est tiré parmi **toutes les variantes des thèmes du boss** (`backgroundsForThemes`) → ajouter une variante d'un thème l'ajoute automatiquement au pool des boss ciblant ce thème. Les sprites idle et décors sont **extraits vers `public/`** par `scripts/copy-boss-sprites.mjs` (jamais servir depuis `assets/`) : boss "réels" = copie de frames individuelles ; boss "low boss" CraftPix = **découpe de spritesheet** (frameWidth = largeur/nb_frames, hauteur = pleine ; comptes de frames explicites par pack car non-carrés parfois, ex. mushroom 70×64). Le boss du jour est tiré **une fois puis figé** dans la table `daily_boss` (une ligne par `(user_id, day_date)`, **aucune policy UPDATE/DELETE**) via `resolveDailyBoss` (`app/actions/boss.ts`, lazy au chargement de l'Arène comme la génération récurrente), en **excluant les boss des 2 derniers jours** (`pickDailyBoss`, pur, testé). Le décor est tiré parmi les `backgroundIds` du boss (`pickBackgroundId`). `VersusScene` reçoit boss+décor en props (plus rien de codé en dur). **Écran de test interne** `app/roster-preview-8f3a2c9d/page.tsx` : chemin **volontairement obscur, non listé, login requis, `noindex`** — permet de vérifier chaque boss (extraction sprite + cohérence décor + orientation via toggle flip) ; ne jamais le lier depuis l'UI. ⚠️ L'orientation `flip` des boss a été posée par hypothèse (réels=false, low boss=true) — **à confirmer visuellement** via l'écran de test.

**Mise à jour issue #74 (2026-07-30)** : le roster passe de 12 à 27 boss (15 ajouts depuis des variantes de packs CraftPix jusque-là inexploitées, + 1 fix : `satyr` pointait vers un sprite humain au lieu du vrai satyre). Chaque frame idle de boss est désormais recadrée sur sa bbox alpha union (`trimBossFrames` dans `copy-boss-sprites.mjs`) pour uniformiser le ratio personnage/canvas entre tous les boss — sans ce recadrage, ce ratio variait de 0.49 à 0.72 selon le pack source, donnant à chaque boss une taille visuelle différente à hauteur CSS fixe. Les hauteurs de rendu dans `VersusScene.tsx` sont passées de `h-28` (112px, héros et boss) à `h-[88px]` (héros) / `h-24` (96px, boss) pour répondre à un retour utilisateur (héros trop grand sur mobile) tout en gardant le héros « à peine » plus petit que le boss.

**Mode Entraînement — génération au chargement, pas seulement au Réveil (US-17)** — Les routines (`recurring_templates`, `weekdays int[]` lundi=0, désactivation sans DELETE) génèrent leurs instances (`tasks` normales, `is_recurring=true` + `recurring_template_id`) via `generateRecurringInstances` (`app/actions/recurring.ts`). **Piège d'intégration** : Le Réveil bloquant ne se monte **que s'il y a des restes** — brancher la génération uniquement en fin de Réveil raterait les jours « propres » (nouvelle routine, zéro reste de la veille). Donc la génération est appelée **au chargement de `app/page.tsx`** (avant le fetch des tâches du jour), lazy et **idempotente** : `planRecurringGeneration` (pur) saute toute routine ayant déjà une instance aujourd'hui — fraîche OU **reste reporté** de cette routine (anti-doublon D5) — et ne génère **jamais** pour un jour passé (D6, seul `today`). `weekdayOf(dayDate)` dérive le jour de semaine de la date locale sans ré-appliquer de fuseau (même logique que `weekKey`). Jour de repos (`recurring_rest_days`) et souscriptions push (`push_subscriptions`, US-11) sont les deux seules tables du projet avec une policy DELETE (préférences de planning réversibles / données techniques d'appareil, pas des données de combat protégées par RG-04). Édition d'un template = **futur seulement** (B4), ne touche jamais les instances déjà créées. Gestion : `/vestiaire/entrainement`. **Dette assumée MVP** : la création se fait via l'écran de gestion, pas via un toggle « récurrente » dans le champ d'ajout de l'Arène (repoussé).

**Le Tableau de Chasse — écran lecture seule dérivé (US-10)** — `app/tableau-de-chasse/page.tsx` ne mute **rien** (B1) : tous les agrégats viennent de `tableauChasseStats` (`lib/game-engine.ts`, pur, testé) sur les `day_results` (fetch borné à 90 jours, tri desc) + `profiles` + solde d'or dérivé (`goldBalance`). `winRate` garde la division par zéro ; `bestDay` départage les égalités par la date la plus récente et vaut `null` si tous les jours sont à 0 dégât. Le **Journal** pagine côté client (`CombatJournal`, « charger plus ») sur le lot déjà chargé, sans re-fetch. Sparkline + anneau = SVG purs statiques (reduced-motion par nature). Accès **via Le Vestiaire** (nav = hub Le Vestiaire), pas d'onglet direct. Les 3 états UI (Loading via `loading.tsx`, Error, Empty) sont obligatoires (règle projet n°3).

**Rage Quit vs Annihiler (`abandon_reason`, US-15)** — Les deux posent `is_abandoned=true` (RG-04, jamais de DELETE) mais portent une **émotion opposée**, distinguée par `tasks.abandon_reason` : `rage_quit` (abandon **punitif** d'une tâche active du jour, en cours de combat → malus **−5 XP clampé sans de-level** via `applyRageQuitPenalty`, ≠ `applyXpDelta` qui peut redescendre de niveau ; punchline « le Boss ricane ») vs `annihilated` (reste nettoyé **sereinement** au Réveil, aucun malus). Le malus est appliqué **une fois par action** (rage-quit d'une racine à N enfants = −5 XP, pas −5×N) ; la cascade sur les sous-tâches actives est calculée par `collectAbandonCascade` (pur). L'**undo** (`undoRageQuit`, même jour) ne restaure que les lignes `abandon_reason='rage_quit'` et rembourse +5 XP — un « Annihiler » n'est pas annulable par ce chemin. Migration `20260721090000` (colonne nullable + check contraint aux deux valeurs). `abandonTask` générique **supprimé** au profit de `rageQuitTask`.

**Perfect / K.O. en direct (US-16)** — Le déclenchement de la célébration est une **fonction pure de transition** `koOutcome(prevBossHp, nextBossHp, bossMaxHp, heroHp)` (`lib/game-engine.ts`) : `null` sauf transition→0 valide, `perfect` si Héro à 100 HP (aucun reste non résolu), sinon `ko`. La garde `prevBossHp === 0` évite le re-déclenchement sans **renaissance** (ajouter une tâche après KO re-heal le Boss puis un nouveau KO re-joue). `Arena.tsx` mémorise le HP **avant** le coup (`previousHp`) pour alimenter la garde. Le palier de série (US-12 : 7/30/100) déclenche la super-variante flammes — calculé en forçant l'issue du jour à `victory`. L'overlay (`PerfectOverlay.tsx`) porte un CTA **« Terminer la journée »** (clôture manuelle, non-bloquante) + « continuer ». Le pop d'entrée `ko-burst` utilise un easing en overshoot **assumé** (juice d'arcade Street Fighter, cf. `PRODUCT.md`) — le hook impeccable le signale comme "bounce-easing", c'est un choix de design volontaire, pas un défaut. Variante douce sous `prefers-reduced-motion`.

**Partage de victoire — paramètres explicites, pas de lookup DB (US-20)** — La route `app/api/share-card/route.tsx` (`next/og` natif à Next.js 16, **aucune dépendance `@vercel/og` séparée** — vérifié dans `node_modules/next/dist/docs`) reçoit toutes les valeurs de la carte en **paramètres de requête explicites** (`lib/share-card.ts`, `buildShareCardParams`/`parseShareCardParams`), jamais par lookup `day_result` : `PerfectOverlay` se déclenche *avant* la clôture du jour, aucune ligne `day_results` n'existe encore à cet instant (le Boss peut même renaître si une tâche est rajoutée après le K.O., cf. note sur `koOutcome`). Contrepartie assumée : la route ne vérifie pas que les valeurs reçues correspondent à un combat réel (n'importe qui pourrait forger une carte en bidouillant les paramètres) — l'authentification Supabase reste un garde-fou anti-abus basique, pas un contrôle d'intégrité. **Cache `Cache-Control: public, immutable, max-age=31536000`** : conséquence assumée, un cache CDN partagé peut resservir l'image à un utilisateur différent une fois qu'une requête identique a été mise en cache, sans re-vérification d'auth — acceptable ici car aucune donnée privée n'est exposée dans l'image. Police `BoldPixels` réservée aux libellés courts/majuscules (nombres, « DODOJO », « VS » — cf. `ASSETS.md` § Fonts) ; tout texte français long ou accentué (pseudo, titre, nom de héros/boss, date) reste sur la police par défaut de Satori pour garantir le rendu des accents. Table `share_events` (analytics minimal `share_clicked`/`share_succeeded`/`share_downloaded`) suit la même convention RG-04 : aucune policy UPDATE/DELETE. **Piège Satori découvert en vérification manuelle** : un style JSX `transform: undefined` (flip conditionnel du sprite Boss selon `boss.flip`) plante le rendu (`failed to pipe response`) — Satori exige une valeur CSS concrète, `"none"` échoue aussi (« Unexpected token type: word »), seule une fonction `scaleX(1)`/`scaleX(-1)` passe. Toujours fournir une valeur `transform` de repli valide (jamais `undefined`/`"none"`) dans un template `ImageResponse`. Par ailleurs `vitest.config.ts` n'avait aucun alias `@/*` (jamais nécessaire tant que seuls des tests `lib/**` sans imports `@/` existaient) — ajouté (`resolve.alias`) pour permettre aux tests composants (`components/**/*.test.tsx`, Testing Library + `jsdom`) d'importer `@/lib/...`/`@/app/...`. Ces tests composants doivent aussi nettoyer le DOM explicitement (`afterEach(cleanup)` de `@testing-library/react`) : sans `globals: true` dans la config Vitest, le cleanup automatique de Testing Library (qui dépend d'un `afterEach` global) ne se déclenche pas.

**Deadlines horaires — détection par polling, pas de replay (US-05)** — L'icône ⏰ sur `TaskRow` (racine et sous-tâche) ouvre un popover `<input type="time">` (`components/combat/DeadlineControl.tsx`) qui fixe/modifie/efface `tasks.deadline_at` (colonne déjà existante en base, aucune migration). La conversion heure locale ↔ ISO passe par `deadlineIso`/`localTimeFromIso` (`lib/game-engine.ts`), DST-aware via itération à point fixe — voir l'entrée dédiée `deadlineIso` ci-dessus (technique différente de `dayKey`, qui formate directement via `Intl.DateTimeFormat` sans arithmétique d'offset). Le franchissement d'une deadline est détecté par un **polling client** (`Arena.tsx`, ~45s, uniquement pendant que l'Arène est montée) : `missedDeadlineTasks` recalcule à chaque tick, et seules les tâches **nouvellement** franchies (suivies via un `Set` de refs, pas de comparaison d'égalité de tableau) déclenchent l'animation « Attaque Surprise » (clignotement de la jauge Héros + `FloatingText` `anchor="hero"` + toast « Repousser +1h »). **Pas de replay au chargement** : les deadlines déjà ratées avant l'ouverture de l'app sont incluses dans le calcul HP dès le premier rendu mais ne redéclenchent jamais l'animation. **Le report du Réveil (US-08) efface la deadline** (`deferOverdueTask`/`deferAllOverdue` posent `deadline_at: null`) pour éviter de cumuler le malus -10 (deadline ratée) avec le malus -20 (retard reporté) déjà appliqué sur la même tâche.

**Cron push — Inngest, pas de schedule par utilisateur (US-11, refactor 2026-07-30)** — Le palier **Hobby** de Vercel (cf. Stack technique) limite les Cron Jobs natifs (`vercel.json`) à **1 exécution/jour**, incompatible avec la fenêtre 17h30 heure locale multi-fuseaux. Un premier essai (workflow GitHub Actions planifié) a **échoué à 100%** en prod (crédits GHA épuisés, `schedule` GitHub Actions massivement étranglé sur repo privé) sans que personne ne le voie — aucune alerte n'existait sur cet échec. Remplacé par **Inngest** : un cron **statique** `reminder-fanout` (`lib/inngest/functions/reminder-fanout.ts`, `*/15 * * * *` UTC) sélectionne les profils éligibles (`buildCandidatesFromDb` + `selectReminderEligibleProfiles`, `lib/push-eligibility.ts`) puis émet un event `push/send-reminder` par profil, consommé par la fonction `send-reminder` (`lib/inngest/functions/send-reminder.ts`) qui envoie la notif web-push. **Pas de schedule par profil/fuseau** : `inngest.schedules.*` n'existe pas dans le SDK (0 occurrence dans `node_modules/inngest` — vérifié avant d'écrire le code, ne pas réintroduire cette hypothèse) ; le fan-out `*/15` couvre tous les fuseaux (y compris les offsets :30/:45) et relit `profiles.timezone` à chaque run, sans état de schedule à réconcilier. **Déterminisme obligatoire** : Inngest ré-exécute tout code hors `step.run` à chaque retry — `now`/`dayKey`/la variante de copy sont calculés une fois par le fan-out et voyagent dans l'event (`SendReminderEvent`), jamais recalculés côté `send-reminder`. Synchronisation Vercel↔Inngest via l'**intégration officielle du Marketplace Vercel**, qui provisionne bien `INNGEST_SIGNING_KEY`/`INNGEST_EVENT_KEY` — **mais la sync des fonctions elle-même n'est pas fiable à chaque déploiement en pratique** (constaté le 2026-07-30 : 0 requête sur `/api/inngest` en 6h sur 5+ déploiements prod successifs, l'app n'apparaissait même pas côté Inngest Cloud). Si le dashboard Inngest (section **Apps**, pas Functions) affiche « No functions found » après un déploiement, resynchroniser à la main : « Sync new app » avec l'URL `https://dodojo.vercel.app/api/inngest`. Vérifier ce point après **tout** futur déploiement touchant ce domaine, ne pas supposer que la sync a eu lieu. `INNGEST_SIGNING_KEY` est **obligatoire en Production** : sans elle, `/api/inngest` (exempté de la garde de session comme toute route `/api/*`, cf. entrée suivante) accepte des requêtes non signées. **Aucun rollback réel** : un revert du merge PR1 restaurerait la route + le workflow GHA, mais ce mécanisme n'a jamais fonctionné en prod — le seul recours en cas de panne Inngest est le déclenchement manuel de `reminder-fanout` depuis son dashboard. Toujours pas de `vercel.json` dans ce repo (volontairement, cf. Stack technique). CI GitHub Actions inopérante faute de crédits au moment de ce refactor — gate de merge = vérification locale (`lint`, `test`, `tsc --noEmit`, `build`, `e2e`), voir `docs/superpowers/plans/2026-07-30-push-inngest-migration.md`.

**Garde de session (`proxy.ts`) — routes techniques exemptées côté anonyme uniquement (US-11)** — `proxy.ts` (Middleware Next.js, renommé depuis `middleware.ts` en Next 16) a un matcher qui couvre tout sauf les assets statiques, donc y compris `/api/*` : sans exemption, `lib/supabase/middleware.ts` redirigeait toute requête sans cookie Supabase vers `/welcome`, y compris les appels externes légitimes (Inngest sur `/api/inngest`, webhooks/OAuth). `isPublicRoute(path)` (`lib/supabase/middleware.ts`, testée dans `lib/supabase/middleware.test.ts`) exempte désormais tout `/api/*` en plus de `/login`/`/welcome`, mais **uniquement pour le garde anonyme** (`!user && !isPublicRoute`) — le garde inverse (utilisateur déjà connecté redirigé loin d'une page publique) reste volontairement restreint à `/login`/`/welcome` seuls, jamais `/api/*` : sinon un utilisateur authentifié appelant une route `/api/*` protégée par sa propre logique (ex. `/api/share-card`, US-20) serait bounced vers `/` avant même d'atteindre son handler. US-03 (webhook Siri) bénéficie de l'exemption anonyme sans rien refaire ; US-22 (Gemini/OAuth) étend `isPublicRoute` à `/oauth/` et `/.well-known/`.

**Token webhook Siri hashé, jamais en clair (US-03)** — `profiles.webhook_token_hash` (SHA-256, `lib/webhook-token.ts`) + `webhook_token_created_at`/`webhook_token_last_used_at`. Le texte en clair n'est retourné qu'une fois, à la génération/régénération (`regenerateWebhookToken`, `app/actions/webhook-token.ts`) — jamais relu depuis la base ensuite. Régénérer écrase simplement le hash (invalidation immédiate du raccourci existant), ce n'est pas une donnée soumise à RG-04 (pas d'historique de combat). La route `POST /api/webhook/add-task` utilise le client Supabase **service-role** (comme `app/api/cron/push-reminders`, US-11), sans cookie, avec un `user_id` explicite retrouvé par hash — la logique d'insertion + recalcul HP est extraite dans `lib/task-insertion.ts` (`insertTaskForUser`) pour être appelée aussi bien par `addTask` (session cookie) que par ce webhook (aucune session), fondation réutilisée telle quelle par le futur US-22 (Gemini MCP). **Piège Vitest** : `vitest.config.ts` n'a pas de résolution d'alias `@/` (pas de plugin `vite-tsconfig-paths`) — tout fichier chargé directement par un test (`lib/task-insertion.ts`, `lib/task-title.ts`, `lib/webhook-token.ts`, `app/api/webhook/add-task/route.ts`) doit importer ses dépendances en **relatif**, jamais via `@/` (même contrainte déjà posée sur `app/sw.ts` par US-11).

**Serveur OAuth 2.1 + MCP pour Gemini (US-22)** — Dodojo implémente lui-même un serveur d'autorisation OAuth 2.1 (PKCE S256 obligatoire, `lib/pkce.ts`) car Supabase Auth n'est pas un serveur OAuth conforme au spec MCP pour des clients tiers. Trois tables (`oauth_clients`/`oauth_authorization_codes`/`oauth_tokens`) ont une **policy DELETE autorisée** — contrairement à `tasks`/`day_results` (RG-04), ce sont des données techniques opérationnelles (jetons/codes), jamais un historique de combat. Enregistrement dynamique de client **ouvert** (RFC 7591, `POST /oauth/register`) : n'importe quel client MCP peut s'auto-enregistrer, protégé par un rate limit basique par IP **en mémoire** (`lib/rate-limit.ts`, best-effort — ne survit pas à un cold start serverless, pas de garantie distribuée entre instances Vercel). `POST /oauth/authorize` valide `redirect_uri` contre la liste enregistrée du client **avant** toute redirection (jamais de redirection vers un `redirect_uri` non vérifié — prévention d'open redirect). Le serveur MCP (`/api/mcp`, transport Streamable HTTP, un seul tool `add_task`) réutilise **strictement** `insertTaskForUser` (`lib/task-insertion.ts`, US-03) — aucune seconde implémentation du calcul HP. Le statut « Gemini connecté » affiché au Vestiaire (`lib/oauth-gemini.ts`) identifie les clients Gemini par une heuristique sur `client_name` (`ILIKE '%gemini%'`) — la DCR n'impose aucun identifiant stable, **hypothèse à revalider** si Google impose un jour un format de nom différent. **Piège garde de session** : `proxy.ts`/`lib/supabase/middleware.ts` (`updateSession`) exempte désormais explicitement `/api/*`, `/oauth/*` et `/.well-known/*` de la redirection anonyme-vers-`/welcome` et connecté-vers-`/` — découvert en implémentant US-22 (les appels serveur-à-serveur de Gemini n'ont aucun cookie Supabase), corrige rétroactivement le même trou latent pour `/api/webhook/add-task` (US-03) et `/api/cron/push-reminders` (US-11). Toute future route technique appelée sans session cookie navigateur doit vérifier qu'elle tombe bien sous l'un de ces trois préfixes, sinon l'ajouter explicitement. **Piège TypeScript découvert en implémentation** : typer un paramètre de fonction en `ReturnType<typeof createClient>` (au lieu du type `SupabaseClient` importé de `@supabase/supabase-js`) fait perdre l'inférence de `@supabase/supabase-js` sur `.insert(...)`, qui résout alors vers `never[]` et casse la compilation (`tsc --noEmit`) dès qu'un client Supabase créé dans une fonction est passé en paramètre à une autre (`app/oauth/token/route.ts`, `app/oauth/revoke/route.ts`, `app/api/mcp/route.ts`) — toujours utiliser le type `SupabaseClient` explicite pour un client service-role passé entre fonctions, jamais `ReturnType<typeof createClient>`. **Aucun test e2e sur le handshake Gemini réel** (dépendance externe non reproductible en CI) : une vérification manuelle post-déploiement avec un vrai compte Gemini est **obligatoire** avant de considérer l'US terminée — l'écosystème « Connected Apps » MCP de Gemini évolue vite, les détails exacts (transport imposé, format de métadonnées) peuvent différer de ce qui est implémenté ici.

**Vérification manuelle post-déploiement effectuée (issue #104) : Gemini Spark, hébergeant les « Custom apps », est indisponible en EEE — root cause côté Google, pas Dodojo** — les endpoints prod (`/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource`) répondent correctement (conformes RFC 8414/9728), l'implémentation Dodojo n'est pas en cause. Les hypothèses initiales de l'issue #104 (statut du consent screen Google Cloud, account-linking, scopes) visaient en réalité **Gemini Enterprise Agent Platform** (produit entreprise, IAM/OAuth client type Okta/Azure AD) — mécanisme sans rapport avec ce qui est implémenté ici. Le mécanisme grand public pertinent s'appelle **« Custom apps for Spark »** : l'utilisateur colle lui-même une URL de serveur MCP dans Gemini > Paramètres > Apps connectées — aucun listing, aucune vérification Google, aucun statut de consent screen à surveiller ; Dodojo ne « apparaîtrait » donc jamais spontanément dans une liste, la feature ne fonctionne pas ainsi. **Vérifié en direct sur un compte réel (Android, France)** : la section « Custom apps »/MCP n'existe pas du tout dans les réglages Gemini — seules des intégrations pré-construites (Spotify etc., partenariats Google directs, mécanisme totalement différent et sans rapport avec RFC 7591) y figurent. Cohérent avec le rollout du produit **Gemini Spark**, qui exclut aujourd'hui l'EEE/UK/Suisse/Nigeria (revue de conformité AI Act européen en cours, aucune date officielle ferme) — root cause de #104, indépendante de toute config Dodojo, rien à corriger côté code pour rendre la fonctionnalité disponible aujourd'hui. Issue laissée ouverte, à retester quand Google étendra Gemini Spark à l'EEE.

**Tenues/skins des héros — recolor par tiers de qualité (US-53)** — Aucun art alternatif n'existe dans `assets/MC` (fichiers `.aseprite` : 3 calques `bkg`/`base`/`effects`, pas de calque peau/armure séparé) ; les tenues sont donc **générées offline** par `scripts/generate-hero-skins.mjs` (jamais au runtime), à partir des frames idle déjà extraites (`public/sprites/mc/<slug>/idle/`). **Volume Intérieur & registre de copy (US-49/US-54)** — Tous les textes "voix" (narration de La Voix + répliques Boss) sont centralisés dans `lib/copy/` (un fichier pur par domaine : `combat.ts`, `rituals.ts`, `rage-quit.ts`, `deadline.ts`, `errors.ts`, `notifications.ts`), chaque scénario exportant une fonction `(level, args) => string` sur `AggressivityLevel = "doux" | "direct" | "brut"` (`types/index.ts`, colonne `profiles.aggressivity_level`, défaut `direct`). **Seuls les textes "voix" sont leveled** — le chrome UI neutre (labels de boutons, placeholders) reste inline, non concerné, recensé mais pas migré (cf. audit `docs/superpowers/specs/2026-07-23-audit-textes-dictionnaire.md`). Réglable dès l'onboarding (nouvelle étape entre avatar et soumission) et à tout moment via la section « Volume Intérieur » du Vestiaire (`updateAggressivityLevel`, `app/actions/profile.ts`) — pas de contrainte one-shot comme le pseudo. Le dictionnaire des notions de l'app (Le Réveil, Rage Quit, Perfect, Combo...) produit pour l'audit #49 est un **document interne**, jamais exposé en UI ni ajouté au Guide (seule l'existence du réglage Volume Intérieur lui-même est documentée dans Le Guide, section « Régler le Volume Intérieur »). **Pools de variantes (retour post-livraison)** : chaque texte "body" (pas les tags courts type `koHeader`/`levelUpTitle`) porte 5-6 variantes par niveau via `lib/copy/variant.ts` (`pickVariant(pool, seed)`) plutôt qu'une chaîne unique, pour éviter la répétition en usage réel. **Piège de stabilité** : le `seed` doit être calculé **une seule fois au déclenchement de l'évènement**, jamais recalculé à chaque re-rendu — sinon le texte change sous les yeux de l'utilisateur pendant qu'il le lit (l'Arène re-rendre toutes les ~45s via le poll deadline, US-05). Convention : `useState(randomSeed)` dans le composant overlay lui-même quand il est démonté/remonté par instance (`PerfectOverlay`, `LevelUpOverlay`, `CrepusculeRecap`, `WakeUpRitual`) ; seed géré explicitement côté `Arena.tsx` (état sibling ou résolu dans le state au moment du `set...`) pour les blocs inline sans mount dédié (empty state, confirmation Rage Quit, toast deadline). Niveau 3 "Street" peut désormais casser le 4ᵉ mur (clins d'œil à l'appli/au jeu elle-même) sur les variantes sparring/street générées — jamais sur sensei, qui reste hors de cette fiction méta.

**Migrations Supabase hors-ordre : `supabase db push` les ignore sans le signaler comme un blocage durable (bug prod #70)** — Deux migrations (`20260723110000_create_oauth_mcp.sql`, `20260723130000_add_profile_aggressivity_level.sql`) sont restées **non appliquées en production** pendant plusieurs jours, cause racine de 3 bugs simultanés (onboarding et Volume Intérieur du Vestiaire en échec sur `profiles.aggressivity_level` inexistante ; Gemini ne pouvait jamais s'auto-enregistrer faute de table `oauth_clients`). Cause : `20260723110000` porte un timestamp **antérieur** à des migrations déjà appliquées (`20260723120000`/`20260723120100`) — `supabase db push --linked` refuse alors de l'insérer par défaut (« Found local migration files to be inserted before the last migration on remote database ») et exige `--include-all`. Ce refus est une erreur explicite en sortie de commande, mais **rien ne le fait remonter automatiquement** (pas de check CI, pas de hook `predeploy`) : une fois vu une fois et non traité, il repasse inaperçu indéfiniment. `npx supabase migration list --linked` (colonnes Local vs Remote) est la commande de vérité pour détecter un écart — **à lancer avant de merger toute PR qui ajoute un fichier dans `supabase/migrations/`**, en plus du build/tests locaux déjà obligatoires (cf. Workflow Git). Toujours nommer les migrations avec un timestamp strictement postérieur à la dernière migration existante sur `main` au moment de la création du fichier, pas au moment du merge (un rebase peut réordonner l'historique de fichiers sans réordonner leurs timestamps).

**Le Réveil (`WakeUpRitual`) : overlay client qui ne déclenche jamais de refetch — toute donnée modifiée pendant le rituel doit être remontée explicitement (bug prod #70)** — `WakeUpRitual` mute la base via des server actions (`deferOverdueTask`, `deferAllOverdue`, `completeOverdueTask`, `annihilateOverdueTask`…) puis, une fois tous les restes traités, appelle `onResolved()` qui ne faisait que `setShowWakeUp(false)` côté `Arena.tsx` — jamais de `router.refresh()` ni de re-fetch. `Arena.tsx` garde son propre state `tasks` initialisé une seule fois depuis les props serveur (`initialTasks`, capturées **avant** l'ouverture du rituel) : une tâche reportée ("Reporter") était donc correctement ramenée au jour courant en base, mais invisible dans l'Arène jusqu'au prochain rechargement complet — un effet visuellement indiscernable d'un "Annihiler". `revalidatePath("/")` (appelé côté serveur par ces actions) invalide le cache de route Next.js mais ne pousse aucune donnée vers un composant client déjà monté sans navigation. Correctif : `deferOverdueTask`/`deferAllOverdue` renvoient désormais les lignes mises à jour (`TaskActionResult.deferredTasks`) ; `WakeUpRitual` les accumule (`useRef`, pas besoin de re-render dessus) et les passe à `onResolved(deferredTasks)` ; `Arena.tsx` les fusionne dans son state (`setTasks(prev => [...prev, ...deferredTasks])`). Règle générale : toute mutation faite **à l'intérieur** d'un overlay client bloquant qui doit rester visible après sa fermeture doit soit renvoyer les lignes affectées pour fusion explicite côté parent, soit déclencher un `router.refresh()` — `revalidatePath` seul ne suffit jamais pour un state client déjà hydraté.

**Navigation : `BottomNav` partout, `BackLink` seulement pour remonter d'un niveau (audit UX 2026-07-24)** — `components/ui/BottomNav.tsx` (3 onglets Arène/Vestiaire/Marché Noir) est monté sur **tous** les écrans authentifiés, pas seulement l'Arène : Le Vestiaire, Tableau de Chasse, Le Guide (index + article), Mes Routines passent `active="vestiaire"` (ils sont tous atteints depuis Le Vestiaire, aucun onglet dédié) ; Le Marché Noir passe `active="marche-noir"`. Ne jamais réintroduire un lien texte ad-hoc "Retour au Vestiaire"/"Retour à l'Arène" — il devient redondant dès que `BottomNav` est présent et recrée l'incohérence corrigée par l'audit (4 styles de retour différents trouvés : position haut/bas, flèche ou non, couleur variable). `components/ui/BackLink.tsx` est le seul pattern de retour restant, réservé à la remontée d'un niveau **à l'intérieur** d'un sous-flux non couvert par un onglet (Guide article → sommaire du Guide) ; ne pas l'utiliser pour retourner à un onglet déjà accessible via `BottomNav`.

**Favicon généré, jamais édité à la main** — `scripts/generate-pwa-icons.mjs` (déjà source de vérité pour `public/icons/*` et `app/apple-icon.png` depuis `public/icons/logo-source.svg`) génère aussi `app/favicon.ico` via un encodeur ICO maison (`buildIco`, frames PNG 16/32/48 embarquées — format supporté nativement depuis Windows Vista/tous navigateurs modernes, pas de dépendance ajoutée). Avant l'audit du 2026-07-24, `favicon.ico` était un fichier orphelin (triangle générique) sans rapport avec la marque, resté silencieusement obsolète car rien ne le régénérait. Si `logo-source.svg` change, relancer `npm run generate:icons` régénère les 6 fichiers (icons PWA + apple-icon + favicon) en une passe — ne jamais committer un `favicon.ico` produit autrement.

**`useFocusTrap` (`hooks/useFocusTrap.ts`) — point d'entrée unique pour tout overlay bloquant (audit #67, PR2)** — confine Tab/Shift+Tab dans un conteneur, restaure le focus au déclencheur à la fermeture. `onEscape` **omis** = overlay volontairement non-dismissable (`WakeUpRitual`, US-08 : Echap ne doit rien faire tant que les restes ne sont pas résolus) ; `onEscape` **fourni** = fermeture standard sur Echap (les 7 autres overlays de l'app). Toujours placer `ref`/`role`/`aria-modal` sur le même élément (celui qui contient réellement les contrôles focusables), pas sur un `div` de backdrop englobant.

**`hp`/`xp` bruts jamais en couleur de texte sur fond neutre — `hp-text`/`xp-text` dédiés (audit #67, PR3)** — `--color-hp`/`--color-xp` (`app/globals.css`) sont calibrés pour le pairing `ink`-sur-couleur-pleine (boutons), pas pour l'usage inverse : utilisés en `text-hp`/`text-xp` sur `bg`/`surface`/`surface-2`, ils tombent à 3.4-3.9:1 (sous 4.5:1 AA). `--color-hp-text`/`--color-xp-text` (même teinte/chroma, L plus élevé) sont réservés à cet usage. Ne jamais réintroduire `text-hp`/`text-xp` bruts sur un fond neutre — seuls `bg-hp`/`bg-xp`/`border-hp`/`border-xp` restent corrects avec les tokens de base.

**`react-hooks/preserve-manual-memoization` (eslint-config-next) bloque `useCallback`/`React.memo` mal formés, même sans React Compiler actif** — cette règle (bundlée par `eslint-config-next`, pas de flag `experimental.reactCompiler` dans `next.config.ts` à ce jour) exige que le tableau de dépendances d'un `useCallback`/`useMemo` corresponde exactement à son inférence statique, y compris des setState pourtant stables par convention React — plus strict que l'`exhaustive-deps` classique. Tenté sur `Arena.tsx`/`TaskList.tsx`/`TaskRow.tsx` (audit #67, PR4) pour réduire les re-renders du poll deadline ~45s, abandonné : aurait demandé de stabiliser toute la chaîne de handlers (`bumpComboOptimistic`/`resetCombo`/`triggerPulse`/`triggerXpPulse` en plus des 4 handlers principaux) sur le fichier le plus critique de l'app, pour un gain P1 marginal. À reconsidérer seulement si le projet active un jour `experimental.reactCompiler` (le composant serait alors automatiquement memoïzé par le compilateur, rendant le `useCallback` manuel inutile de toute façon).

**Flake e2e « utilisateur test introuvable » — root cause confirmée : JWT Admin GoTrue rejeté sous concurrence, guéri par retry (`listUsersRetrying`/`deleteUserRetrying`, `e2e/fixtures.ts`)** — la piste documentée le 2026-07-24 (JWT ES256 `kid <nil>` intermittent) est désormais **reproduite à la demande** : 20 appels séquentiels à `admin.auth.admin.listUsers()` passent systématiquement, mais une rafale de 10 appels concurrents en déclenche systématiquement une partie en échec (403 `bad_jwt`), et **un retry immédiat guérit 100% des échecs observés** (8/8 sur rafale répétée) — confirme qu'il s'agit d'un flake d'infra externe (projet Supabase lié), jamais d'un bug de code ou d'ordre d'exécution des specs. Toute la logique de résolution `email → uid` de `e2e/fixtures.ts`/`e2e/global-setup.ts` passe désormais par `listUsersRetrying` (export de `fixtures.ts`, 3 tentatives) plutôt qu'un appel direct — **ne jamais réintroduire un appel direct `admin.auth.admin.listUsers()`/`deleteUser()` dans ce dossier**, toujours passer par l'helper retry (`deleteUserRetrying` pour la suppression). Le bug concret trouvé en creusant : `resetOnboardingUser` appelait `admin.auth.admin.deleteUser(u.id)` sans jamais vérifier son `error` — un échec silencieux laissait le compte de test en place, et le signup suivant échouait sur « email déjà utilisé » (`onboarding.spec.ts`, timeout 30s sur `waitForURL("/onboarding")`) : symptôme sans rapport apparent avec la cause réelle, un cas d'école de ne jamais ignorer le second membre `{ data, error }` d'un appel Admin GoTrue.

**dnd-kit : capture de pointeur résiduelle après un drag simulé Playwright — un clic ultérieur peut se perdre silencieusement (`e2e/nesting-dnd.spec.ts`)** — flake observé uniquement en run complet (jamais en isolation, ni via bump du timeout du hook à 60s — écarté comme piste, cf. historique) : le bouton « × » (Abandonner) de la tâche traitée juste après un drag reste marqué `:active` en snapshot Playwright sans jamais ouvrir sa modale de confirmation (`role="alertdialog"` absent du DOM). `PointerSensor` de dnd-kit appelle `setPointerCapture()` sur `pointerdown` pour suivre le drag au-delà des bornes de l'élément ; la séquence `mouse.down()` → deux `mouse.move()` → `mouse.up()` de `dragOnto` ne dispatche aucun `pointermove` **après** le `mouseup`, et dans certains runs la capture reste résiduelle côté navigateur — un clic suivant sur un autre bouton est alors livré à l'élément qui détenait la capture plutôt qu'à sa cible réelle. Correctif : un `page.mouse.move()` supplémentaire juste après `mouse.up()` dans `dragOnto` (`e2e/nesting-dnd.spec.ts`), forçant la relâche complète — validé sur 3 runs complets consécutifs (0 échec) après l'avoir reproduit une fois sans lui. Si ce flake réapparaît sur un **autre** test drag & drop, appliquer le même correctif plutôt que de bump un timeout (déjà tenté, sans effet — la modale ne s'ouvrait pas du tout, ce n'était pas un problème de marge).

**Reframe "Le Démon Intérieur" — vocabulaire complet renommé, pas juste le sens (issue #51)** — Le concept narratif est passé de "Dojo de Rue" (Sensei mentor externe, Boss rival de rue, vibe Ryu/Ken) à "Le Démon Intérieur" : le Boss est tout ce qui traîne non tranché dans la tête du joueur, "La Voix" (ex-Sensei) est sa propre discipline qui lui parle depuis l'intérieur. **Tout le vocabulaire japonais/martial-arts a été purgé**, pas seulement recadré en sens — identifié en cours de brainstorming comme un vernis externe plaqué, incohérent avec un concept devenu intime : `Sensei` → **La Voix** (voix intérieure) / **Doux** (palier Volume Intérieur), `Dojo Gauge` → **Volume Intérieur**, `Sparring`/`Street` → **Direct**/**Brut**, `Rituel du Réveil` → **Le Réveil**, `Rituel du Crépuscule` → **Dernier Round**, `Ceinture Jaune`/`Ceinture Noire`/`Sensei` (titres streak) → **Calme**/**Silence**/**Esprit Vide**, `QG` → **Le Vestiaire**, `Échoppe` → **Le Marché Noir**, `Panthéon` → **Tableau de Chasse**, `Manuel du Dojo` → **Le Guide**. Restent inchangés (vocabulaire gaming universel, pas martial-arts) : `Dodojo` (nom de l'app), `Boss`, `Héros`, `Arène`, `K.O.`, `Perfect`, `Combo`, `Rage Quit`. **Deux migrations de données** ont été nécessaires (`profiles.aggressivity_level` et `profiles.current_title`, valeurs déjà persistées pour les profils existants) — tout futur ajout de palier/titre doit garder le lexique en tête, ne jamais réintroduire de vocabulaire dojo/japonais. Un bug réel a été trouvé en exécutant la suite e2e après le renommage du type : `createProfile` (`app/onboarding/actions.ts`) dupliquait `AggressivityLevel` en dur avec les anciennes valeurs et retombait silencieusement sur `"sparring"` (devenu invalide en base) — **toute valeur d'un type partagé dupliquée en dur ailleurs que dans `types/index.ts` est une dette qui casse silencieusement au prochain renommage**, préférer systématiquement l'import du type. Spec complet : `docs/superpowers/specs/2026-07-24-demon-interieur-identite-design.md`.

**Auto-reorder à l'ajout (issue #111) : exclure les tâches abandonnées du pool, rollback jamais sur une fermeture stale** — `handleAdd`/`handleAddSubtask` (`Arena.tsx`) appellent `reorderSiblingsAction` quand des racines/sous-tâches sont déjà complétées, pour insérer la nouvelle tâche juste au-dessus. Le pool passé (`roots`/`siblings`) doit exclure les tâches `is_abandoned` : `reorderSiblings` (`app/actions/tasks.ts`) rejette toute tâche abandonnée (« Cette tâche est introuvable »), et sur un compte qui accumule des Rage Quit/Annihiler au fil du temps (RG-04, jamais de DELETE), une seule racine abandonnée suffit à faire échouer le reorder. **Symptôme trompeur** : diagnostiqué au départ comme une lenteur réseau/Supabase (`toggle-cascade.spec.ts`/`nesting-dnd.spec.ts`/`rafale-optimistic.spec.ts` timaient sur `Déplacer "<titre>"` en attente d'un état `enabled`) — la trace réseau a montré le POST `addTask` répondant en <350ms à chaque fois ; le vrai bug était le rollback en cas d'erreur du reorder (`setTasks(previousSnapshot)`) qui utilisait un snapshot capturé **avant** l'ajout optimiste (fermeture de `handleAdd`, jamais réévaluée), donc effaçait la tâche qui venait d'être créée avec succès (orpheline en base, invisible tant que la page n'est pas rechargée) au lieu d'annuler seulement le reorder. Le rollback restaure désormais uniquement les `position` réellement modifiées, capturées depuis le `prev` réel du `setTasks` optimiste. Toujours suspecter un vrai bug de state avant de bumper un timeout d'assertion e2e sur un flake reproductible — un run isolé avec `--trace on` + inspection de `0-trace.network` (`npx playwright show-trace`) tranche vite entre latence réseau réelle et requête rapide suivie d'un state cassé côté client.

**Combo server-authoritative, module l'XP réelle (issue #115)** — Le combo (`comboLabel`/`comboIntensity`, `lib/game-engine.ts`) n'est plus purement visuel : il ne monte que si deux tâches sont cochées à moins de 15 min d'intervalle (`nextComboState`, fenêtre glissante `COMBO_WINDOW_MS`) et ajoute un bonus d'XP par palier (`xpForCompletion`/`comboXpBonus` : x2=+5, x3=+10, x4=+15, non cappé). L'état (`profiles.combo_count`/`last_combo_completed_at`) est **server-authoritative** — cohérent avec le fait que l'XP est déjà calculée uniquement côté serveur (`setTaskCompleted`, le client ne fait que de l'optimistic UI toujours écrasé par la réponse serveur). Décocher une tâche **rembourse exactement** le montant réellement accordé à sa complétion (`tasks.xp_awarded`, nullable — fallback `XP_PER_TASK` pour une tâche complétée avant cette migration) plutôt qu'un flat `XP_PER_TASK`, pour ne jamais désynchroniser l'économie XP. Décocher et Rage Quit cassent tous les deux la série (`combo_count=0`). Le client garde un guess optimiste local (même fenêtre de 15 min, `lastComboCompletedAtRef`) pour le feedback instantané, resynchronisé silencieusement sur la valeur serveur après coup — même patron que `level`/`xp`.

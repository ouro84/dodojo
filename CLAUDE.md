## Règle de mise à jour de ce fichier

Ce fichier est un critère de merge. Toute PR ou modification qui introduit un nouveau piège, modifie une convention, ou solde une dette documentée ici doit obligatoirement mettre ce fichier à jour dans le même commit.

Cas déclencheurs :

## Ce projet en une phrase

Une application de productivité mobile-first de style RPG/Arcade 16-bits où chaque tâche créée soigne le Boss de la journée (+20 HP) et chaque tâche complétée lui inflige des dégâts, offrant une gratification immédiate pour vaincre la procrastination.

## Conventions — non négociables

### Langue d'échange
Toute communication avec l'utilisateur se fait en français, sans exception. Les termes techniques, noms d'API, de librairies, de variables, de commandes et le vocabulaire spécifique (ex: "commit", "fetch", "hook", "state") restent en anglais quand c'est l'usage naturel du domaine.

### Changelog (`CHANGELOG.md`)
Toute PR qui livre une feature (produit ou technique) ajoute sa ligne sous `## [Unreleased]` de `CHANGELOG.md`, dans le même commit que l'implémentation — jamais après coup. Format des versions : `XX.YY.ZZ` (Majeure.Mineure.Fix), aligné sur les releases GitHub. À chaque release GitHub effective, le contenu d'`[Unreleased]` est basculé dans une nouvelle section versionnée et datée.

### Documentation utilisateur (Le Guide — issue #68)
Avant de pousser une PR, **vérifier systématiquement si elle nécessite une doc utilisateur** et, le cas échéant, la produire **dans la même PR** :
- **Nouvelle feature visible par l'utilisateur** (écran, mécanique, règle de jeu) → **créer un nouvel article** dans la base Notion « Guide Dodojo » (catégorie appropriée parmi `ORDRE_SECTIONS`, `Statut = Publié`, `Slug` en minuscules/tirets, stable une fois publié — c'est l'URL `/guide/<slug>`).
- **Changement d'un comportement déjà documenté** (barème, rituels, streaks, or, combos, roster…) → **mettre à jour l'article Notion existant** (même `Slug`, ne jamais le renommer une fois publié — casserait les deep-links `StreakBadge`/Le Vestiaire/liens externes).
- **Source = Notion**, base « Guide Dodojo » : éditer/ajouter la page, `Statut = Publié`, puis `npm run pull:guide` pour régénérer `content/guide/<slug>.md` + `content/guide/index.json` (committés dans la PR). Si Notion n'est pas accessible (`NOTION_TOKEN` absent), éditer directement les fichiers `content/guide/<slug>.md`/`index.json` en respectant le schéma (`lib/guide.ts`), en **gardant les `Slug` stables**.
- **Uniquement si pertinent** : une PR purement technique/refactor/infra (sans impact sur ce que voit ou comprend l'utilisateur) n'exige **pas** de doc utilisateur — ne pas en inventer.

### Commits (Conventional Commits)
Format strict : `type: description courte`
- `feat:` Nouvelle fonctionnalité (ex: `feat: add screen shake animation on damage`)
- `fix:` Correction de bug (ex: `fix: prevent negative gold balance`)
- `chore:` Tâches de maintenance (ex: `chore: setup vitest config`)
- `docs:` Documentation technique uniquement.

### Workflow Git
- `main` est protégée. Aucun commit direct. Déploiement automatique sur Vercel.
- Une branche par fonctionnalité : `feat/us-XX-nom-feature`.
- **Zéro merge si la CI est rouge.** Tous les tests Vitest et l'application doivent build sans erreur.
- **Zéro PR poussée sur GitHub tant que les tests (Vitest + Playwright e2e) n'ont pas été passés en local.** Une fois la CI en place, elle vient en double sécurité, pas en remplacement de cette vérification locale.

## Règles de code

1. **TypeScript Strict :** Interdiction d'utiliser `any`. Tout type doit être explicitement déclaré (notamment les états de tâches et profils).
2. **Logique isolée dans `lib/` :** Tout algorithme de calcul de jeu (formule d'XP, calcul dynamique des HP maximum du Boss) doit résider dans `lib/game-engine.ts` pour être testé sans dépendances de rendu UI.
3. **Gestion des 3 états UI :** Tout écran (Arène, Le Vestiaire) doit obligatoirement implémenter un état de chargement (Loading), un état d'erreur (Error), et un état vide (Empty - ex: quand le Boss est K.O.).
4. **Pas de suppression destructive :** Les tâches ne doivent jamais être supprimées via un `DELETE` SQL. Utiliser exclusivement la colonne `is_abandoned` ou `is_completed` pour maintenir l'historique et la jauge du Boss (RG-04).

## Pièges et décisions non-évidentes

> Les post-mortems clos sans risque de récidive vivent désormais dans `docs/INCIDENTS.md` (déplacés depuis ce fichier le 2026-09-17 pour désencombrer ce qui est lu à chaque tâche). Cette section ne garde que les invariants encore actifs et les leçons de méthode réutilisables.

**Décalage horaire et étanchéité du jour** — Le "jour" du jeu est le jour **local** de l'utilisateur, jamais l'UTC. `dayKey(date, timezone)` (`lib/game-engine.ts`) le calcule depuis `profiles.timezone` (IANA, captée à l'onboarding) ; toutes les écritures `day_date` en dépendent. Le Boss ne voit que les tâches du jour local courant (RG-03) ; les restes d'un jour passé passent par Le Réveil (US-08) avant toute nouvelle action.

**`deadlineIso` (US-05) : l'offset DST se recalcule au point fixe, jamais probé une seule fois** — `deadlineIso(dayDate, timeHHMM, timezone)` convertit une heure locale en ISO UTC. Calculer l'offset une seule fois à l'instant "naïf" est faux pour une heure valide juste avant une transition DST (l'instant naïf tombant après elle) : ça retombe sur l'offset post-transition, décalage d'1h silencieux, sans erreur ni crash. Le correctif recalcule l'offset à l'instant candidat obtenu (itération à point fixe, 2 passes suffisent).

**Pas de policy DELETE en RLS** — Les tables `profiles` et `tasks` n'ont volontairement aucune policy Supabase RLS pour `DELETE`. Ceci applique RG-04 au niveau base de données, en plus de la convention côté application (colonnes `is_abandoned` / `is_completed`).

**Pas de trigger d'auto-création de profil** — Aucun trigger sur `auth.users` ne crée automatiquement une ligne `profiles` à l'inscription. Le pseudo doit être défini explicitement par l'utilisateur, donc la création de la ligne `profiles` fait partie du flow d'onboarding applicatif (US-14), pas de la migration SQL.

**Jauge de HP du Héros — pool pondéré, dégâts verrouillés jamais recalculés à la baisse (US-05/issue #191)** — `calculateHeroHp` (`lib/game-engine.ts`) combine un pool pondéré par tâche (-20 HP retard reporté, -10 HP deadline horaire ratée, plancher à 0) avec un `lockedDamage` en 2ᵉ paramètre. Résoudre une pénalité ne heal plus la jauge : `tasks.hp_penalty` verrouille le poids sur une tâche du jour courant résolue tardivement, `profiles.hp_damage_locked`/`hp_damage_locked_day` agrègent le dégât des restes résolus via Le Réveil (qui changent de `day_date`, donc invisibles autrement). `Arena.tsx` anticipe ce verrouillage côté client de façon optimiste — sinon la jauge heal visuellement le temps d'un refresh. `WakeUpRitual` calcule sa propre jauge sur `overdueTasks` figé au montage, jamais sur `tasks` qui rétrécit en direct pendant le rituel.

**Cycle de la Journée & table `day_results`** — Les deux bornes du jour sont Le Réveil (US-08, ouverture) et « Terminer la journée » (US-07, clôture non-bloquante). `day_results` (une ligne par `(user_id, day_date)`, aucune policy DELETE) enregistre l'issue du jour, écrite de façon idempotente (upsert, recalculée depuis les tâches) via `app/actions/day.ts`. `revalidatePath("/")` est interdit "during render" en Next 16 : `backfillMissedDaysDuringRender()` mute sans revalider, `backfillMissedDays()` (appelée aussi au chargement d'`app/page.tsx`, pas seulement en fin de Réveil) revalide après le render.

**Profondeur des sous-tâches (RG-01) appliquée uniquement côté applicatif** — La colonne `parent_id` de `tasks` n'a aucune contrainte SQL limitant la profondeur à 2 niveaux. La garde repose sur `isNestableParent`/`planReorder` (`lib/game-engine.ts`), revérifiés côté UI et côté server action (`reorderSiblings`). Dette assumée : une action serveur appelée hors UI reste la seule ligne de défense, pas de filet base de données.

**Web Speech API : geste utilisateur direct obligatoire** — `SpeechRecognition.start()` (`hooks/useSpeechToText.ts`) doit être appelée de façon synchrone dans le handler `onClick` du bouton micro, sans détour asynchrone. Safari/iOS rejette silencieusement l'activation du micro sinon. La détection de support navigateur passe par `useSyncExternalStore` avec un snapshot serveur toujours `false`, pour éviter un mismatch d'hydratation.

**Web Speech API : `interimResults = false` n'est pas garanti par tous les moteurs — toujours vérifier `isFinal` (issue #211)** — certains moteurs (Android Chrome notamment) livrent quand même plusieurs `onresult` avec un transcript grandissant avant le résultat final, malgré la demande contraire. Comme `MicButton` appelle `onTranscript` (donc `addTask`) directement à chaque `onresult`, sans champ texte intermédiaire, chaque évènement interim créait sa propre tâche ("c", "co", "cou"...). `useSpeechToText` ne déclenche désormais `onResult` que si `event.results[event.results.length - 1].isFinal` est vrai — jamais se fier au seul flag `interimResults` posé à la construction.

**E2E Playwright : serveur prod toujours, série+1 compte en local, 4 workers isolés par compte en CI** — `playwright.config.ts` démarre toujours un serveur **prod** (`build && start`), jamais `next dev` (qui compile à la demande et sature sous parallélisme). En local, un seul compte e2e fixe (ADR-04) → `workers: 1`, `fullyParallel: false` (les tests mutent le même état sinon). En CI, `workers: 4` / `fullyParallel: true` : chaque worker utilise son propre compte Supabase, résolu via `TEST_PARALLEL_INDEX` (worker 0 → compte historique, 1-3 → comptes secondaires provisionnés par `scripts/e2e-provision-worker-account.mts`). Tous les helpers admin de `e2e/fixtures.ts` résolvent le compte du worker **courant** via `getE2eAdmin()` — passer `workers>1` sans ça mélangerait silencieusement les comptes UI et les comptes seedés par les fixtures.

**dnd-kit : `autoScroll` par défaut fausse la détection de collision sur les gestes fins** — `DndContext` a `autoScroll={false}` explicitement. Un scroll automatique pendant le drag décale les coordonnées utilisées pour décider "réordonner avant" vs "imbriquer" (`isTopHalfDrop`, `Arena.tsx`). Si l'auto-scroll doit revenir un jour, recalculer la géométrie depuis `onDragMove` en direct plutôt qu'une capture figée avant le drag.

**Économie d'or dérivée & Marché Noir de héros (US-18)** — L'or n'est jamais accumulé : `gold` = `SUM(day_results.gold_earned) − SUM(unlocked_heroes.price_paid)` (`goldBalance`, `lib/game-engine.ts`) ; `profiles.gold` n'est qu'un cache. Catalogue statique `lib/heroes.ts`, rendu idle via le pipeline spritesheet `CharacterSprite` (jamais un composant idle dédié). Possession dans `unlocked_heroes` (unique `(user_id, hero_id)`, aucune policy DELETE, achat idempotent) ; `fire_knight` a un prix non nul depuis l'US-29 (plus de possession d'office). Tarif plat 500 or depuis l'issue #122 (plus de graduation 150-350), non rétroactif sur les `price_paid` historiques.

**Streaks à budget de jokers hebdo (US-12)** — `currentStreak` (`lib/game-engine.ts`) compte les victoires consécutives mais tolère jusqu'à 2 non-victoires par semaine ISO (`weekKey`) ; la 3ᵉ casse. Dérivée de `day_results` (source unique) ; `profiles.streak_days`/`best_streak` sont des caches rafraîchis à la clôture et au backfill. `titleForStreak`/`profiles.current_title` n'existent plus (remplacés par le catalogue de succès, cf. entrée dédiée plus bas).

**Onboarding & économie du starter (US-29)** — Tunnel : `/welcome` (signup **client-side**, jamais une server action — sinon le cookie de session ne se propage pas ; « Confirm email » doit être OFF côté Supabase) → `/onboarding` (pseudo → avatar) → Arène avec coach. `/` redirige vers `/welcome` si non-auth. `isHeroOwned(id, ownedIds)` ne renvoie plus `true` d'office pour le héros par défaut — possession strictement via `unlocked_heroes`, le starter choisi est offert (`price_paid=0`) à `createProfile`. Coach du 1er combat piloté par `profiles.has_seen_tutorial` (garde `useRef`, une seule fois).

**Le Guide — articles Notion, sync auto au build (issue #68)** — `content/guide/<slug>.md` + `content/guide/index.json` (committés), rendus statiquement (SSG, `dynamicParams = false` — un slug hors du set résolu au build 404 au niveau routage, jamais de rendu à la demande). Source de vérité = base Notion « Guide Dodojo » (`Statut = Publié`). Sync via le hook `prebuild`, **tolérant** : token absent ou panne réseau ⇒ contenu committé conservé, le build ne casse jamais. Slugs stables = anciens `section.id` (deep-links `StreakBadge`/Le Vestiaire). **Piège Notion** : un lien Markdown relatif (`[texte](/chemin)`) posé dans une page Notion est silencieusement réécrit en URL absolue vers `app.notion.com` à l'enregistrement — jamais utilisable comme lien interne à l'app, préférer du texte brut pour référencer une autre page de l'app depuis un article du Guide. **Piège de séquence** : éditer `content/guide/` à la main pour un nouvel article se fait écraser au build suivant si Notion ne connaît pas encore ce slug — toujours créer la page dans Notion d'abord, puis `npm run pull:guide`. Chaque pull peut aussi rapporter une divergence Notion↔repo préexistante et sans rapport avec la tâche en cours — ne jamais la committer par réflexe, isoler uniquement les fichiers du nouvel article.

**Roster de Boss & décors dynamiques — 27 boss depuis l'issue #74** — Le boss (et son décor) du jour ne sont plus codés en dur. Catalogues purs : `lib/bosses.ts` (chaque boss porte `idleFrameCount`, `backgroundThemes` cohérents avec son lore, et `flip` car le boss est à droite et doit regarder le héros) + `lib/backgrounds.ts` (16 variantes sur 7 thèmes). Le décor du jour est tiré parmi les variantes des thèmes du boss (`backgroundsForThemes`) — ajouter une variante d'un thème l'ajoute automatiquement au pool. Boss+décor du jour tirés une fois puis figés dans `daily_boss` (une ligne par `(user_id, day_date)`, aucune policy UPDATE/DELETE) via `resolveDailyBoss`, en excluant les boss des 2 derniers jours. Chaque frame idle est recadrée sur sa bbox alpha union (`trimBossFrames`, `scripts/copy-boss-sprites.mjs`) pour uniformiser le ratio personnage/canvas entre packs sources hétérogènes (variait de 0.49 à 0.72 sans ce recadrage). Écran de test interne `app/roster-preview-8f3a2c9d/page.tsx` (chemin obscur, login requis, `noindex`, jamais lié depuis l'UI) pour vérifier chaque boss. `boss.flip` s'applique aussi au bust de `VsIntroOverlay` (intro VS/FIGHT!), pas seulement au sprite de combat de `VersusScene` — le miroir `scaleX(-1)` doit vivre sur un wrapper distinct, jamais sur l'élément qui porte l'animation CSS de slide-in (qui écrase silencieusement tout `transform` inline posé sur ce même nœud).

**Boss qui change à la première visite du jour — récidive suspectée de #160 bug#1, root cause non confirmée (issue #212, ouverte)** — l'upsert+relecture inconditionnelle de `resolveDailyBoss` (voir ci-dessus) est mathématiquement race-safe pour deux appels concurrents sur le même jour, et le scénario déjà couvert par `e2e/boss-race.spec.ts` (chargement + ajout de tâche quasi simultané) passe. Le symptôme revu ("première visite du jour", pas lié à un ajout de tâche) ne colle pas à ce trigger — piste non confirmée : même famille que le prefetch RSC qui exécute un composant serveur complet (issue #156, sur `generateRecurringInstances`). En attendant une preuve réelle (Vercel Hobby ne garde qu'1h de logs, donc pas de vérification a posteriori) : log de diagnostic dans `resolveDailyBoss` (à retirer une fois confirmé) + `prefetch={false}` sur `BottomNav` en filet défensif, coût nul (pages dynamiques, `staleTimes.dynamic` vaut déjà 0 par défaut).

**Sprites de combat — spritesheets, boîte de recadrage commune et hauteurs figées (issue #48)** — Tous les personnages sont rendus depuis des spritesheets horizontales (`public/sprites/**/anim/<anim>.png`) via `SpriteAnimator` (`steps()` CSS) et `CharacterSprite` (machine à états `idle|attack|hurt|death`). La boîte de recadrage d'un personnage est l'**union alpha de toutes ses anims**, jamais par anim — sinon le perso change de taille au démarrage d'une attaque. `renderScale` se dérive donc de `LEGACY_IDLE_HEIGHTS` (`scripts/build-sprite-sheets.mjs`), mesurée sur les anciennes frames idle et figée — jamais recalculée depuis la nouvelle boîte, sous peine de rétrécir tous les personnages. Alias `hurt` → `take_hit` (`CharacterSprite.tsx`) pour les héros qui nomment leur anim différemment des boss. `animKey` doit être posé en `key` React sur le nœud animé (`SpriteAnimator.tsx`) — changer la durée/l'itération d'une animation CSS déjà en cours sur le même nœud ne la relance pas à 0. Les dégâts sont calés sur la frame d'impact (~40% par défaut, `IMPACT_FRAME_OVERRIDES` pour recaler) et les rafales sont coalescées (retrigger frame 0 + somme des dégâts, flush forcé à 1200ms). Sous `prefers-reduced-motion`, le gating est désactivé (jauges/chiffres/`PerfectOverlay` instantanés) ; `playwright.config.ts` force `reducedMotion: "reduce"` pour toute la suite sauf `combat-animations.spec.ts`. La transition d'état après la fin d'une anim est une fonction pure `nextAnimStateAfterEnd` (`lib/combat-animation.ts`) appliquée symétriquement côté héros (`onHeroAttackEnd`) et côté Boss (`onBossStateEnd`) — sans elle, l'état interne `heroAnim`/`bossAnim` d'`Arena.tsx` reste figé après un `hurt` et bloque toute contre-attaque ultérieure. **Piège de test** : l'attribut `data-anim-state` expose l'état interne de `CharacterSprite` (`rendered`), qui se corrige tout seul — il ne prouve rien sur le state `Arena.tsx` réellement lu par les gardes anti-chevauchement. VFX d'impact = flash blanc (`filter: brightness(0) invert(1)`, dérivé de `rendered === "hurt"`, jamais de la prop `state` externe). Ancrage horizontal : `idleAnchorX`/`idleWidthRatio` centrent la silhouette idle à 25%/75% de la scène (`VersusScene.tsx`), l'ancre du Boss étant miroitée (`1 - idleAnchorX`) quand `flip` est vrai.

**Mode Entraînement — génération au chargement + 3 verrous anti-doublon (US-17/issue #156)** — `generateRecurringInstances` (`app/actions/recurring.ts`) tourne au chargement d'`app/page.tsx` (pas seulement en fin de Réveil, qui ne se monte que s'il y a des restes). `planRecurringGeneration` (pur) saute toute routine ayant déjà une instance aujourd'hui ou un reste actif d'un jour antérieur de cette routine, et ne génère jamais pour un jour passé. Trois verrous : (1) `profiles.last_recurring_gen_day` est un cache de saut écrit **après** succès, jamais un verrou pris en amont ; (2) un index unique **partiel** `tasks_recurring_unique_per_day` (`where recurring_template_id is not null and is_abandoned = false`) ferme la course de double-génération induite par le prefetch RSC de `<Link href="/">` ; (3) `.upsert(..., { onConflict })` ne peut pas cibler un index partiel (PostgREST génère un `ON CONFLICT` sans le `WHERE`, rejeté `42P10`) — l'insertion se fait donc ligne par ligne, chaque `23505` étant une course perdue (no-op), pas une erreur.

**Le Tableau de Chasse — écran lecture seule dérivé (US-10)** — `app/tableau-de-chasse/page.tsx` ne mute rien : tous les agrégats viennent de `tableauChasseStats` (`lib/game-engine.ts`, pur) sur `day_results` + `profiles` + `goldBalance`. `winRate` garde la division par zéro ; `bestDay` départage les égalités par la date la plus récente. Accès via Le Vestiaire, pas d'onglet direct.

**Rage Quit vs Annihiler (`abandon_reason`, US-15)** — Les deux posent `is_abandoned=true` (jamais de DELETE) mais `abandon_reason` distingue `rage_quit` (malus -5 XP clampé sans de-level, `applyRageQuitPenalty`) de `annihilated` (aucun malus, nettoyage serein au Réveil). Le malus s'applique une fois par action (cascade sur sous-tâches incluse, pas ×N). L'undo (`undoRageQuit`, même jour) ne restaure que les lignes `rage_quit` et rembourse +5 XP.

**Perfect / K.O. en direct (US-16)** — `koOutcome(prevBossHp, nextBossHp, bossMaxHp, heroHp)` (`lib/game-engine.ts`) est une fonction pure de transition : `null` sauf transition→0 valide, `perfect` si Héros à 100 HP, sinon `ko`. La garde `prevBossHp === 0` évite le re-déclenchement sans renaissance (ajouter une tâche après KO re-heal le Boss).

**Quand un compte de test « accumule », vérifier ce qui régénère de l'état à chaque chargement avant de conclure que les données elles-mêmes traînent** — `generateRecurringInstances` tourne à chaque chargement de `/` : purger `tasks` sans purger `recurring_templates` (+ remettre `profiles.last_recurring_gen_day` à `null`) donne l'illusion d'un reset alors que chaque run régénère une instance par template accumulé, gonflant la baseline HP du Boss et ralentissant les specs qui recalculent sur toutes les tâches du jour.

**`[WebServer] Error: Internal: NoFallbackError` dans la sortie e2e : c'est notre propre test de 404, pas une erreur à investiguer** — c'est le signal de contrôle interne de Next pour « param hors du set prérendu et pas de fallback », soit `dynamicParams = false` sur `app/guide/[slug]/page.tsx` — la seule route de l'app dans ce cas. Next l'attrape et rend le 404 ; l'erreur fuit juste sur stderr. **Invariant à retenir** : une occurrence par run = normal ; **plus d'une = autre chose renvoie un 404 sur une route `dynamicParams = false`**, et ça mérite un coup d'œil.

**Trois timeouts Playwright indépendants : `timeout` (budget par test), `expect.timeout` (par assertion), `webServer.timeout` (démarrage du serveur)** — à régler séparément, l'un ne relève pas les autres (le défaut Playwright pour `expect` reste 5s tant qu'`expect: { timeout }` n'est pas posé explicitement dans `playwright.config.ts`, quel que soit le `timeout` par test). Sur un échec CI e2e, télécharger l'artefact `playwright-report` et lire `error-context.md` (état réel de la page rendu) + la timeline réseau du trace **avant** de toucher au code — ça distingue en deux minutes une assertion trop courte d'un vrai bug d'état, et donne le chiffre qui justifie la marge choisie.

**Assertions e2e sur un état d'animation transitoire : échantillonner, jamais poller — et ne jamais garder une référence de nœud DOM à travers une mutation de HP** — un état qui n'apparaît qu'une fois pendant quelques centaines de ms (`hurt`, `attack`) est régulièrement raté par le poll de `expect` (qui recule 100ms→1000ms). Correctif : une boucle `requestAnimationFrame` posée par `page.evaluate` avant le déclencheur, qui enregistre la **suite** des états, puis assertion sur cet historique. `Arena.tsx` re-keye le bloc contenant `VersusScene` à chaque mutation de HP (toute action qui change les HP change `pulse`) — un `MutationObserver` posé avant coup devient orphelin dès la mutation suivante, donnant un faux négatif sur les deux personnages à la fois. Corollaire pour toute boucle qui vide le Boss : la condition de sortie doit être `aria-valuenow === 0`, jamais un compteur de tours arbitraire (un compte e2e partagé accumule des données au fil du temps et peut dépasser n'importe quelle borne fixe).

**Notifications avant deadline — event Inngest par tâche, `cancelOn` + re-check DB, jamais de replay (issue #114)** — `schedule-deadline-reminder.ts` dort (`step.sleepUntil`) jusqu'à `deadlineAt − offsetMinutes`, puis **relit la base** avant d'envoyer (tâche toujours active, `reminder_enabled`, `deadline_at` inchangé) ; `cancelOn: task/deadline-reminder-cleared` supprime le run en amont dès qu'une action mute la tâche, mais ce re-check reste un filet en profondeur volontaire. `idempotency` inclut `offsetMinutes` (pas seulement `taskId`+`deadlineAt`) — le snooze réémet le même event avec un offset synthétique différent, sans lui il serait à tort dédoublonné contre le premier. Le snooze repousse le **rappel**, jamais la deadline elle-même — contourner silencieusement la pénalité HP via une action de notif serait contraire à la philosophie du jeu.

**Cabinet desktop de l'Arène — fond étendu suit le décor réel du jour, jamais un asset figé (issue #167)** — `.arena-shell` (`app/globals.css`, dédiée à l'Arène seule, 64rem à partir de `lg:` — les écrans HUD plats gardent `.screen-main`/42rem) et `ArenaBackdrop` réutilisent `background.publicPath` — le décor RÉEL résolu par `resolveDailyBoss`, jamais un asset fixe (un gradient CSS écrit à part se désynchroniserait du fond réellement affiché dès qu'un autre thème que celui testé manuellement sort). Masqué <1024px, `object-cover`, jamais de blur/`backdrop-filter` (interdit par DESIGN.md — profondeur plate).

**`unlocked_heroes` ne peut jamais être vidé sans reseed `fire_knight`** — la quasi-totalité des specs de combat ne passent jamais par un reset boutique et supposent `fire_knight` déjà possédé et équipé (offert à l'onboarding). `purgeE2eAccountState` (`e2e/fixtures.ts`, seule source de vérité pour la purge de compte e2e — ne jamais dupliquer cette liste de tables ailleurs) réenchaîne systématiquement DELETE + upsert `fire_knight` (`price_paid: 0`) + reset des champs `equipped_hero_id`/`equipped_skin_id`/`equipped_title_code`/`title_manually_set`.

**Suppression de compte : la cascade FK existante suffit, jamais de purge manuelle table par table (issue #154)** — Toutes les FK vers `profiles.id`/`auth.users.id` sont `on delete cascade` depuis les migrations d'origine (`tasks`, `day_results`, `unlocked_heroes`/`unlocked_skins`/`unlocked_achievements`, `daily_boss`, `recurring_templates`, `push_subscriptions`, `share_events`, `oauth_tokens`/`oauth_authorization_codes`). `deleteAccount` (`app/actions/account.ts`) se limite donc à un seul appel `supabase.auth.admin.deleteUser(userId)` via un client service-role (RLS bypass). RG-04 protège l'historique de combat contre l'usage courant (rage quit, décochage) — il ne s'applique pas à une demande d'effacement définitif du compte lui-même (art. 17 RGPD). `exportUserData` (art. 20 RGPD) exclut volontairement `webhook_token_hash` et tout token OAuth brut (fuite potentielle, pas une donnée utile à la portabilité) — ne jamais lever ces exclusions sans revoir cette décision de sécurité.

**Chasse aux emojis — icônes UI/nav, jamais la copy narrative (issue #187)** — Les emojis servant d'icône fonctionnelle (nav, boutons, badges de statut) sont remplacés par `GameIcon` (`components/ui/GameIcon.tsx`) ; les emojis dans la copy narrative (La Voix, toasts, célébrations K.O./Perfect) restent inchangés — pas le même registre, remplacer casserait le rythme de lecture pour un gain nul. `GameIcon` a deux sources non interchangeables : pack `public/icons/ui/*.png` (Raven Fantasy Icons, cf. ASSETS.md) pour les concepts qu'il couvre réellement, SVG dessiné à la main sinon (communication, temps, énergie, export). Certains concepts n'ont aucun équivalent même après recherche exhaustive (aucune lune/nuit dans tout le pack) : garder l'emoji plutôt que forcer un mauvais proxy visuel, décision explicite. Toujours zoomer ×3 chaque candidat avant de le committer — une inspection rapide confond facilement des formes proches sur une feuille de sprites.

**`outline-none` inconditionnel + `focus-visible:outline*` sur le même élément : le focus clavier devient invisible, pas juste "moins visible" (issue #189)** — les deux utilitaires ciblent la même propriété CSS `outline` — l'état "au repos" (toujours actif) gagne, et la variante `focus-visible:outline*` ne s'applique jamais, même quand `:focus-visible` matche réellement. Toujours préférer `ring` (`box-shadow`, propriété différente, insensible à ce conflit) à `outline` quand un `outline-none` de repos coexiste avec un état focus-visible sur le même élément. **Piège de contraste voisin, cause différente** : un `ring` à opacité réduite (ex: `ring-hp/20`) peut techniquement s'afficher tout en tombant sous 3:1 WCAG 1.4.11 — un anneau de focus qui *s'affiche* n'est pas la même preuve qu'un anneau *suffisamment contrasté* (calculer depuis les tokens OKLCH bruts, ne pas estimer à l'œil) ; vérifier les deux séparément avant de clore un constat d'accessibilité.

**Couche domaine `lib/domain/` — client Supabase et userId explicites, jamais de session cookie (issue #201)** — Toute la logique métier des tâches, de la boutique, du boss et de la progression vit sous `lib/domain/`, en fonctions `(supabase: SupabaseClient, userId: string, …)`. Les server actions de `app/actions/` ne font plus que trois gestes : résoudre la session, appeler le domaine, traduire l'erreur puis `revalidatePath`. **Trois interdits sous `lib/domain/`** : `"use server"`, `revalidatePath`, `supabase.auth.getUser()` — un seul suffit à rendre la fonction inappelable depuis le serveur MCP ou le webhook Siri, qui n'ont aucun cookie. Le client est **toujours** typé `SupabaseClient` de `@supabase/supabase-js`, jamais `ReturnType<typeof createClient>`. Le domaine renvoie des **codes** (`DomainErrorCode`, `lib/domain/errors.ts`), jamais de français — le MCP les sert tels quels à un agent, l'UI les habille.

**Scopes OAuth du serveur MCP — défaut restrictif, refus explicite sur l'inconnu (issue #201)** — `lib/oauth-scopes.ts` définit 4 scopes (`tasks:read`/`tasks:write`/`profile:read`/`profile:write`). Une requête `/oauth/authorize` sans paramètre `scope` accorde `tasks:read tasks:write` — jamais `profile:write`. Un scope inconnu est refusé, jamais filtré silencieusement. `lib/mcp-tools.ts` filtre `tools/list` selon le scope du token. **Piège de droits SQL sur toute fonction `security definer`, découvert en vérifiant en direct** : sur un projet Supabase hébergé, `revoke execute ... from public` ne retire que le grant PUBLIC implicite — `alter default privileges` pose par défaut un grant EXECUTE explicite à `anon`/`authenticated` au `CREATE FUNCTION` que ce revoke ne touche pas ; n'importe qui muni de la clé anon pourrait alors appeler le RPC via PostgREST. Toute future fonction de ce type doit `revoke ... from public, anon, authenticated` explicitement, et passer si possible en **security invoker** avec RLS activé sans policy — `service_role` a `BYPASSRLS` et fonctionne à l'identique, tandis qu'un appel `anon`/`authenticated` égaré échoue sur RLS plutôt que de muter la ligne d'une victime.

**Tools MCP — le faux client de test doit filtrer réellement, c'est une frontière de sécurité tenant, pas du sucre de test (issue #201)** — le serveur MCP appelle le domaine avec un client **service-role qui contourne RLS** : les filtres applicatifs (`.eq("user_id", userId)` etc.) sont la seule frontière de tenant qui reste. `FakeQueryBuilder` (`lib/domain/fake-supabase.ts`) doit donc faire réellement filtrer `eq`/`in`/`lt`/`is`/`or`/`select(cols, { count, head })`/`upsert` — chaque no-op rendait toute une classe de filtre `user_id` manquant intestable, sans conséquence tant que RLS protégeait un client cookie-scope mais critique dès qu'un client service-role contourne RLS. `lib/domain/tenant-isolation.test.ts` verrouille l'invariant sur les fonctions du domaine.

**Une écriture correctement scopée, suivie d'une lecture non scopée ou d'un effet de bord inconditionnel, fuite quand même — et rapporte un succès en le faisant** — vérifier le nombre de lignes réellement affectées (`.select("id")` + garde sur la longueur du résultat) avant tout effet de bord ou toute lecture aval, jamais seulement l'absence d'`error`. Une inférence que l'appelant n'a pas la légitimité de faire à partir de "0 ligne affectée" (conclure `task_not_found` alors que ça peut être `task_completed`/`task_abandoned`/un no-op idempotent) doit être discriminée **dans le domaine** par une relecture ciblée sur `id`+`user_id`, jamais déduite côté tool MCP, qui ne voit que le résultat brut de l'UPDATE.

**`parseArgs` renomme les clés du schema MCP — le handler lit les clés produites par le parseur, jamais les noms de propriété d'`inputSchema`** — se tromper renvoie `undefined` silencieusement, sans erreur nulle part (`Record<string, unknown>` non vérifiable par TypeScript). Discipline `undefined` (= ne pas toucher la colonne, ex: les paramètres de rappel de `set_deadline`) vs coercion booléenne stricte (`=== true`/`=== "true"`, sinon refus explicite du type incorrect, jamais un fallback silencieux sur `false`) — les deux formes typent pareil (`boolean`), seule la discipline d'écriture les distingue.

**Enregistrement dynamique de client MCP : n'accepter que https + loopback IPv4 rend le serveur inutilisable par tout client natif (issue #201)** — `isValidRedirectUri` (`lib/oauth-client-registration.ts`) doit couvrir les trois formes de redirection RFC 8252 pour un client natif : §7.1 schéma privé (`monapp:/callback`), §7.2 https revendiqué, §7.3 loopback — **`127.0.0.1` et `[::1]`** (crochets compris dans `new URL(...).hostname`, comparer à `"::1"` seul ne matche jamais). La sécurité ne repose pas sur ce filtre : `app/oauth/authorize/route.ts` refuse déjà tout `redirect_uri` absent de la liste enregistrée du client (anti open-redirect), et l'utilisateur doit consentir — ce filtre-ci n'a qu'à écarter les schémas qui ne sont jamais une redirection (liste noire `javascript:`/`data:`/`vbscript:`/`file:`/`blob:`). **Écart assumé, décidé par l'utilisateur** : `isLoopbackOrPrivateHost` accepte aussi les plages RFC 1918 (`10/8`, `172.16/12`, `192.168/16`) et RFC 4193 (`fc00::/7`) en `http:`, pour les clients auto-hébergés sur LAN. Ce que l'écart coûte : le code d'autorisation traverse le LAN en clair. Ce qui le rend tenable — et qui doit être revérifié avant d'y toucher — c'est le **cumul** de trois garde-fous : PKCE **S256 obligatoire**, code à **usage unique** (supprimé à l'échange), **TTL 60s**. Relâcher l'un des trois rouvre la question. Non couvert volontairement : les noms mDNS `*.local`.

**`NextResponse.redirect()` vaut 307 par défaut et préserve la méthode — mortel pour une réponse OAuth qui suit un POST (issue #201)** — une redirection après un POST doit répondre en **303 See Other**, jamais 307/308, quand la suite attendue est un GET (RFC 6749 §4.1.2 pour la réponse d'autorisation). Règle transposable : quand une redirection suit un POST, la propriété à asserter en test est la **méthode d'arrivée**, jamais l'URL seule — un 307 porte exactement la même URL qu'un 303, donc un test qui ne capture que l'URL ne détecte jamais la régression.

**Écran de consentement OAuth : design system dupliqué inline, contrainte assumée (issue #201)** — `lib/oauth-consent-page.ts` rend une chaîne HTML depuis un Route Handler, hors du pipeline Tailwind (`STYLES` en dur) : contrainte assumée pour rester testable en Vitest sans moteur de rendu React. `STYLES` est un template literal — tout backtick dans un commentaire CSS le termine prématurément, avec une erreur de compilation qui pointe loin du vrai problème. Le nom du client est isolé dans un `<span class="client">` (anti-hameçonnage) : un test qui vérifie la phrase complète doit asserter les deux moitiés séparément, la phrase n'étant plus contiguë dans le HTML. Rendre la page dans un navigateur fait partie de la vérification, au même titre que les tests — un contraste `hp` brut sur fond neutre n'a été attrapé qu'en regardant une capture du rendu, pas en relisant le CSS.

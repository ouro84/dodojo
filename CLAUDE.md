## Règle de mise à jour de ce fichier

Ce fichier est un critère de merge. Toute PR ou modification qui introduit un nouveau piège, modifie une convention, ou solde une dette documentée ici doit obligatoirement mettre ce fichier à jour dans le même commit.

Cas déclencheurs :

## Ce projet en une phrase

Une application de productivité mobile-first de style RPG/Arcade 16-bits où chaque tâche créée soigne le Boss de la journée (+20 HP) et chaque tâche complétée lui inflige des dégâts, offrant une gratification immédiate pour vaincre la procrastination.

## Conventions — non négociables

### Langue d'échange
Toute communication avec l'utilisateur se fait en français, sans exception. Les termes techniques, noms d'API, de librairies, de variables, de commandes et le vocabulaire spécifique (ex: "commit", "fetch", "hook", "state") restent en anglais quand c'est l'usage naturel du domaine.

### Changelog (`CHANGELOG.md`)
Toute PR qui livre une feature (produit ou technique) ajoute sa ligne sous `## [Unreleased]` de `CHANGELOG.md`, dans le même commit que l'implémentation — jamais après coup. Format des versions : `XX.YY.ZZ` (Majeure.Mineure.Fix), aligné sur les releases GitHub. À chaque release GitHub effective, le contenu d'`[Unreleased]` est basculé dans une nouvelle section versionnée et datée.

### Documentation utilisateur (Le Guide — issue #68)
Avant de pousser une PR, **vérifier systématiquement si elle nécessite une doc utilisateur** et, le cas échéant, la produire **dans la même PR** :
- **Nouvelle feature visible par l'utilisateur** (écran, mécanique, règle de jeu) → **créer un nouvel article** dans la base Notion « Guide Dodojo » (catégorie appropriée parmi `ORDRE_SECTIONS`, `Statut = Publié`, `Slug` en minuscules/tirets, stable une fois publié — c'est l'URL `/guide/<slug>`).
- **Changement d'un comportement déjà documenté** (barème, rituels, streaks, or, combos, roster…) → **mettre à jour l'article Notion existant** (même `Slug`, ne jamais le renommer une fois publié — casserait les deep-links `StreakBadge`/Le Vestiaire/liens externes).
- **Source = Notion**, base « Guide Dodojo » : éditer/ajouter la page, `Statut = Publié`, puis `npm run pull:guide` pour régénérer `content/guide/<slug>.md` + `content/guide/index.json` (committés dans la PR). Si Notion n'est pas accessible (`NOTION_TOKEN` absent), éditer directement les fichiers `content/guide/<slug>.md`/`index.json` en respectant le schéma (`lib/guide.ts`), en **gardant les `Slug` stables**.
- **Uniquement si pertinent** : une PR purement technique/refactor/infra (sans impact sur ce que voit ou comprend l'utilisateur) n'exige **pas** de doc utilisateur — ne pas en inventer.

### Commits (Conventional Commits)
Format strict : `type: description courte`
- `feat:` Nouvelle fonctionnalité (ex: `feat: add screen shake animation on damage`)
- `fix:` Correction de bug (ex: `fix: prevent negative gold balance`)
- `chore:` Tâches de maintenance (ex: `chore: setup vitest config`)
- `docs:` Documentation technique uniquement.

### Workflow Git
- `main` est protégée. Aucun commit direct. Déploiement automatique sur Vercel.
- Une branche par fonctionnalité : `feat/us-XX-nom-feature`.
- **Zéro merge si la CI est rouge.** Tous les tests Vitest et l'application doivent build sans erreur.
- **Zéro PR poussée sur GitHub tant que les tests (Vitest + Playwright e2e) n'ont pas été passés en local.** Une fois la CI en place, elle vient en double sécurité, pas en remplacement de cette vérification locale.

## Règles de code

1. **TypeScript Strict :** Interdiction d'utiliser `any`. Tout type doit être explicitement déclaré (notamment les états de tâches et profils).
2. **Logique isolée dans `lib/` :** Tout algorithme de calcul de jeu (formule d'XP, calcul dynamique des HP maximum du Boss) doit résider dans `lib/game-engine.ts` pour être testé sans dépendances de rendu UI.
3. **Gestion des 3 états UI :** Tout écran (Arène, Le Vestiaire) doit obligatoirement implémenter un état de chargement (Loading), un état d'erreur (Error), et un état vide (Empty - ex: quand le Boss est K.O.).
4. **Pas de suppression destructive :** Les tâches ne doivent jamais être supprimées via un `DELETE` SQL. Utiliser exclusivement la colonne `is_abandoned` ou `is_completed` pour maintenir l'historique et la jauge du Boss (RG-04).

## Pièges et décisions non-évidentes

**Décalage horaire et Étanchéité du jour** — Le "jour" du jeu est le **jour local** de l'utilisateur, pas l'UTC. Il est calculé via `dayKey(date, timezone)` (`lib/game-engine.ts`) à partir de la colonne `profiles.timezone` (IANA, captée à l'onboarding via `Intl`). Toutes les requêtes/écritures `day_date` (server actions, `app/page.tsx`) passent par ce jour local. Ceci corrige le bug UTC de l'ancien `todayIso()` (à 01h à Paris on était encore "hier" en UTC) et le cas voyage/changement de fuseau. Le Boss est calculé uniquement sur les tâches du jour local courant (RG-03) ; les restes d'un jour local passé passent par Le Réveil (US-08, processus bloquant) avant toute nouvelle action.

**`deadlineIso` (US-05) : l'offset DST doit être recalculé au point fixe, pas probé une seule fois** — `deadlineIso(dayDate, timeHHMM, timezone)` convertit une heure locale saisie (`<input type="time">`) en ISO UTC. Une première version calculait l'offset du fuseau une seule fois, à l'instant "naïf" (HH:MM interprété directement comme UTC) — correct la plupart du temps, mais faux pour une heure locale valide **avant** une transition DST si l'instant naïf tombe **après** celle-ci : ex. `deadlineIso("2026-03-29", "01:30", "Europe/Paris")` (jour de passage à l'heure d'été, transition à 01h00 UTC) probait l'offset à +2 (post-transition) au lieu de +1 (pré-transition, l'heure réellement demandée), et renvoyait un horodatage décalé d'1h sans erreur ni crash — corruption silencieuse, y compris au round-trip via `localTimeFromIso`. Le correctif recalcule l'offset **à l'instant candidat obtenu**, pas seulement à l'instant naïf de départ (itération à point fixe, 2 passes suffisent pour tout delta DST réel) ; no-op pour toute date loin d'une transition (offset stable → une seule itération change rien).

**Pas de policy DELETE en RLS** — Les tables `profiles` et `tasks` n'ont volontairement aucune policy Supabase RLS pour `DELETE`. Ceci applique RG-04 au niveau base de données, en plus de la convention côté application (colonnes `is_abandoned` / `is_completed`).

**Pas de trigger d'auto-création de profil** — Aucun trigger sur `auth.users` ne crée automatiquement une ligne `profiles` à l'inscription. Le pseudo doit être défini explicitement par l'utilisateur (voir tone of voice : pas de fallback générique type "Héros"), donc la création de la ligne `profiles` fait partie du flow d'onboarding applicatif (US-14), pas de la migration SQL.

**Jauge de HP du Héros — dette soldée par Le Réveil (US-08) + pool pondéré (US-05)** — La jauge de HP du Héros (`calculateHeroHp` dans `lib/game-engine.ts`) n'est plus purement décorative. **Depuis US-05, le pool accepte un poids par tâche** (`HeroHpPenaltyTask`, champ `weight`) au lieu d'un poids fixe -20 pour toute la liste : une tâche en retard reportée d'un jour précédent (`overdueHpPenalties`) pèse -20 HP, une deadline horaire ratée du jour courant et non résolue (`deadlineHpPenalties` + `missedDeadlineTasks`) pèse -10 HP — les deux pools se combinent dans un seul appel à `calculateHeroHp`, plancher à 0. Le Réveil (`components/combat/WakeUpRitual.tsx`, US-08) traite les restes au démarrage via un overlay **bloquant** : Terminé / Reporter / Annihiler (+ actions groupées). **Depuis l'issue #191, résoudre un reste n'efface plus le dégât** (cf. entrée dédiée ci-dessous) — la jauge peut donc rester basse pour le reste de la journée locale, jusqu'au Réveil suivant. Voir le spec unifié `docs/superpowers/specs/2026-07-20-cycle-journee-design.md` et `docs/superpowers/specs/2026-07-22-us05-deadlines-design.md`.

**Suppression du heal Héros — dégâts verrouillés, jamais recalculés à la baisse une fois subis (issue #191)** — Avant cette issue, résoudre une pénalité active (cocher/abandonner une tâche à deadline ratée, reporter/annihiler un reste au Réveil) faisait sortir la tâche des pools live (`overdueHpPenalties`/`deadlineHpPenalties`/`deferredRestHpPenalties`) et la jauge HP Héros remontait aussitôt — un heal ajouté par erreur de conception (issue #101, pulse doré "A3"), contraire à la philosophie voulue : les 100 HP représentent les dégâts subis dans la journée, pas un état recalculé en live sur les seules pénalités encore actives. Deux colonnes complémentaires verrouillent le dégât à la résolution, selon que la tâche reste visible ou non : **`tasks.hp_penalty`** (nullable, jamais réinitialisé à null une fois posé) verrouille le poids (-10/-20) sur une tâche du **jour courant** au moment de sa résolution tardive (`setTaskCompleted`/`rageQuitTask`, calculé par `hpPenaltyToLock` — priorité au reste déféré sur la deadline, mutuellement exclusifs en pratique puisque `deferOverdueTask` efface toujours `deadline_at`) ; **`profiles.hp_damage_locked`/`hp_damage_locked_day`** (cache de saut day-scoped, même patron que `last_recurring_gen_day`, lu via `currentLockedHpDamage`/écrit via `nextLockedHpDamage`) agrège le dégât des restes résolus **via Le Réveil** (`completeOverdueTask`/`annihilateOverdueTask`/`annihilateOverdueOlderThan`) — ces tâches changent de `day_date` ou sortent de toute requête "aujourd'hui", leur dégât ne peut donc pas voyager sur une ligne de tâche visible. `calculateHeroHp` prend désormais un 2ᵉ paramètre `lockedDamage` (simple addition, plancher à 0 inchangé) ; `lockedHpPenalties` (`lib/game-engine.ts`) lit `tasks.hp_penalty` sur les tâches déjà résolues du jour courant, avec un garde `is_completed || is_abandoned` pour éviter un double-comptage si une tâche redevient active puis se re-résout dans la même journée. **`Arena.tsx` anticipe le verrouillage côté client** (`handleToggle`/`handleRageQuit` appellent `hpPenaltyToLock` de façon optimiste avant la réponse serveur) — sans ça, le state client resterait sur `hp_penalty: null` jusqu'au prochain fetch complet et la jauge healerait visuellement le temps d'un refresh. **`WakeUpRitual` calcule sa propre jauge sur `overdueTasks` (figée au montage), jamais sur `tasks`** qui rétrécit au fil de la résolution des restes pendant le rituel — sinon la jauge remonterait à vue pendant Le Réveil lui-même, exactement le heal qu'on supprime ; le total verrouillé renvoyé par le serveur (`TaskActionResult.hpDamageLocked`) voyage par le même canal `onResolved({ deferredTasks, createdTasks, hpDamageLocked })` que le bug #70 (state client déjà hydraté, `revalidatePath` ne le pousse jamais). Migration `20260810210000_remove_hero_hp_heal.sql`.

**Cycle de la Journée & table `day_results`** — Les deux bornes du jour sont Le Réveil (US-08, ouverture, traitement des restes) et « Terminer la journée » (US-07, ex-"Obi-Wan", clôture cérémonielle non-bloquante). La table `day_results` (une ligne par `(user_id, day_date)`, contrainte unique) enregistre l'issue du jour (`victory` / `retreat` / `defeat`), les dégâts, l'XP, etc. — fondation du Tableau de Chasse (US-10), des Streaks (US-12) et du partage (US-20). Écriture **idempotente** (upsert, chiffres recalculés depuis les tâches, jamais accumulés) via `app/actions/day.ts` (`closeDay` à la clôture, `backfillMissedDays` en fin de Réveil pour l'historique sans trous). **Aucune policy DELETE** sur `day_results` (RG-04). "Annihiler" un reste = `is_abandoned = true`, jamais un DELETE. **Issue #160 (bug #2)** : `backfillMissedDays()` est désormais aussi appelée en inconditionnel au chargement d'`app/page.tsx` (même patron lazy/idempotent que `resolveDailyBoss()`), pas seulement en fin de Réveil — un compte qui n'a jamais de tâche en retard ne montait jamais Le Réveil, seul déclencheur historique de ce backfill, laissant tout jour gagné mais jamais clôturé manuellement comme un trou permanent en base (invisible du Tableau de Chasse, qui ne compte que les lignes existantes, mais consommé comme joker par `currentStreak`, qui parcourt le calendrier jour par jour). `revalidatePath("/")` est interdit "during render" en Next.js 16 : la variante `backfillMissedDaysDuringRender()` (`app/actions/day.ts`) fait la mutation sans revalider, `backfillMissedDays()` (nom public inchangé, appelée par `WakeUpRitual` après le render) reste la seule à revalider.

**Profondeur des sous-tâches (RG-01) appliquée uniquement côté applicatif** — La colonne `parent_id` de `tasks` n'a aucune contrainte SQL (check/trigger) limitant la profondeur à 2 niveaux. La garde repose entièrement sur `isNestableParent`/`planReorder` (`lib/game-engine.ts`), revérifiés à la fois côté UI (bouton "+" absent sur une sous-tâche, `planReorder` refuse d'imbriquer une tâche qui a déjà des enfants) et côté server action (`reorderSiblings` dans `app/actions/tasks.ts`). Dette assumée pour le Sprint 1 : une action serveur appelée directement (hors UI) reste la seule ligne de défense, pas de filet base de données.

**Web Speech API : geste utilisateur direct obligatoire** — `SpeechRecognition.start()` (`hooks/useSpeechToText.ts`) doit être appelée de façon synchrone dans le handler `onClick` du bouton micro, sans détour asynchrone avant l'appel. Safari/iOS rejette silencieusement l'activation du micro si `.start()` n'est pas directement dans la pile d'un geste utilisateur. La détection de support navigateur (`SpeechRecognition` absent de `lib.dom.d.ts`, typé dans `types/speech-recognition.d.ts`) passe par `useSyncExternalStore` avec un snapshot serveur toujours `false`, pour éviter un mismatch d'hydratation Next.js entre le rendu serveur (pas de `window`) et le rendu client.

**E2E Playwright : exécution en série + serveur de production obligatoires** — `playwright.config.ts` force `fullyParallel: false` / `workers: 1` et démarre un serveur **prod** (`npm run build && npm run start`), pas `next dev`. Deux raisons cumulées, diagnostiquées en reproduisant le bug (9/9 vert en série, 6-8/9 KO dès 4 workers) : (1) tous les tests partagent l'unique compte e2e fixe (ADR-04), donc en parallèle ils mutent le même état (tâches, boss du jour) et se marchent dessus (contrôles restés `disabled`, redirections manquées) ; (2) `next dev` compile les routes à la demande, et sous parallélisme tous les workers déclenchent cette compilation en même temps, saturent le CPU et font dépasser le timeout de navigation. Ne pas revenir à `fullyParallel` sans d'abord isoler un compte Supabase par worker. Port surchargeable via `E2E_PORT` pour cohabiter avec un `next dev` local sur `:3000`.

**dnd-kit : `autoScroll` par défaut fausse la détection de collision sur les gestes fins** — `DndContext` a `autoScroll={false}` explicitement. Avec l'auto-scroll par défaut de dnd-kit activé, un drag qui approche le bord de la zone scrollable déclenche un scroll automatique **pendant** le geste ; les coordonnées absolues utilisées pour décider moitié haute/moitié basse d'une ligne (`isTopHalfDrop` dans `Arena.tsx`) se retrouvent décalées d'autant, et le geste "réordonner avant" peut basculer silencieusement en "imbriquer". Bug reproduit et diagnostiqué en e2e (Playwright) : la logique pure (`planReorder`, testée en Vitest) était correcte, seule la position live du pointeur dérivait pendant le drag. Si l'auto-scroll doit revenir un jour (listes très longues), il faudra recalculer la géométrie à partir d'un événement `onDragMove` en direct plutôt que d'une capture figée avant le drag.

**Économie d'or dérivée & Marché Noir de héros (US-18)** — L'or n'est jamais accumulé : `gold` = `SUM(day_results.gold_earned) − SUM(unlocked_heroes.price_paid)` (`goldBalance`, `lib/game-engine.ts`). `gold_earned` est écrit à la clôture (`closeDay`) et au backfill (traité **chronologiquement** pour un bonus streak correct) via `computeGoldEarned` (base par issue + part dégâts + bonus streak cappé). `profiles.gold` n'est qu'un **cache**. Le Marché Noir vend des **héros** (et non des skins de Boss — BDD d'origine révisée) : catalogue **statique** `lib/heroes.ts` (pas de table admin), rendu idle via `components/combat/IdleSprite` (frames PNG `/sprites/mc/<slug>/idle/frameNNNN.png`, index base 0 sur 4 chiffres). Possession dans `unlocked_heroes` (unique `(user_id, hero_id)`, **aucune policy DELETE**, RG-04, achat idempotent). `fire_knight` possédé d'office sans ligne (`isHeroOwned`). `profiles.equipped_hero_id` = héros affiché dans l'Arène (`VersusScene`, câblé via `Arena`). Skins/tenues (recolors) = US future ; nav = **hub Le Vestiaire** (Tableau de Chasse/Marché Noir via Le Vestiaire). ⚠️ **Issue #122 — tarif plat depuis le 2026-07-30** : tous les héros du catalogue valent 500 or (plus de graduation 150-350). Le starter choisi à l'onboarding reste offert (`price_paid=0`), mécanique US-29 inchangée. La migration n'est **pas** rétroactive — les `price_paid` historiques restent figés (RG-04 esprit), seuls les futurs achats sont impacted.

**Streaks à budget de jokers hebdo (US-12)** — La série (`currentStreak`, `lib/game-engine.ts`) compte les victoires consécutives mais **tolère jusqu'à 2 non-victoires (retreat/defeat/trou) par semaine ISO** (lundi→dimanche, dérivée du `day_date` local via `weekKey`) ; la 3e casse. Retourne `{ length, jokersUsedThisWeek, atRisk }`. **Changement de sémantique** : un trou isolé n'est plus une rupture (joker toléré). Dérivée de `day_results` (source unique) ; `profiles.streak_days`/`best_streak` sont des **caches** rafraîchis à la clôture (`closeDay`) et au backfill. Les paliers de streak (7/30/100 → Calme/Silence/Esprit Vide) sont désormais des succès du catalogue `lib/achievements.ts` — voir « Système de succès & titres (issue #72) » ci-dessous. `titleForStreak`/`profiles.current_title` n'existent plus. Compteur + alerte « en danger » au Vestiaire (`StreakBadge`), flammes à la victoire à la clôture (US-07 = « Terminer la journée »).

**Onboarding & économie du starter (US-29)** — Tunnel : `/welcome` (signup **client-side**, même patron que `/login` — jamais de server action pour l'auth, sinon le cookie de session ne se propage pas ; **« Confirm email » doit être OFF** côté Supabase) → `/onboarding` (pseudo → avatar) → Arène avec coach. Entrée non-auth : `/` redirige vers `/welcome` (les autres routes protégées gardent `/login`). **Changement d'économie** : `isHeroOwned(id, ownedIds)` ne renvoie **plus** `true` d'office pour le défaut — possession strictement via `unlocked_heroes`. Le starter choisi est offert (ligne `price_paid=0`) à `createProfile` ; `fire_knight` a désormais un prix non nul (sinon gratuit au Marché Noir). Migration de seed pour les profils existants + fixture e2e (`resetShopState` grante `fire_knight`). Coach du 1er combat (`ArenaCoach`, piloté par `profiles.has_seen_tutorial`) : étape « add » (suggestion « Prendre en main Dodojo ») → « strike » → `markTutorialSeen()` une fois (garde `useRef`) ; bouton « Passer » ; punchline « Premier sang » sur `PerfectOverlay` quand le KO tombe coach actif. e2e onboarding = compte dédié recréé à chaque run (`resetOnboardingUser`, creds `.env.local`).

**Le Guide — articles Notion multi-pages, sync auto au build (issue #68)** — Le guide est **statique** : `content/guide/<slug>.md` + `content/guide/index.json` (committés) rendus par `app/guide/page.tsx` (sommaire par catégorie) et `app/guide/[slug]/page.tsx` (article, SSG via `generateStaticParams`, `dynamicParams = false` — un slug hors du set résolu au build 404 au niveau routage, jamais de rendu à la demande ; sans ça, `notFound()` seul renvoie un fallback statique caché en HTTP 200, cf. header `x-nextjs-prerender: 1`). Source de vérité = base Notion **« Guide Dodojo »** (pas une simple page), filtrée sur `Statut = Publié`. **Aucune dépendance SDK Notion** — `scripts/pull-guide.mjs` interroge l'API REST Notion en `fetch` brut (`NOTION_TOKEN` seul requis ; `NOTION_DATABASE_ID` a un défaut hardcodé dans le script, override optionnel). Rendu Markdown via `react-markdown` + `remark-gfm` (`components/guide/ArticleMarkdown.tsx`), pas de `rehype-raw` (le script ne produit que du Markdown pur). **Mode Entraînement — génération au chargement, pas seulement au Réveil (US-17)** — Les routines (`recurring_templates`, `weekdays int[]` lundi=0, désactivation sans DELETE) génèrent leurs instances (`tasks` normales, `is_recurring=true` + `recurring_template_id`) via `generateRecurringInstances` (`app/actions/recurring.ts`). **Piège d'intégration** : Le Réveil bloquant ne se monte **que s'il y a des restes** — brancher la génération uniquement en fin de Réveil raterait les jours « propres » (nouvelle routine, zéro reste de la veille). Donc la génération est appelée **au chargement de `app/page.tsx`** (avant le fetch des tâches du jour), lazy et **idempotente** : `planRecurringGeneration` (pur) saute toute routine ayant déjà une instance aujourd'hui — fraîche OU **reste reporté** de cette routine (anti-doublon D5) — et ne génère **jamais** pour un jour passé (D6, seul `today`). `weekdayOf(dayDate)` dérive le jour de semaine de la date locale sans ré-appliquer de fuseau (même logique que `weekKey`). Jour de repos (`recurring_rest_days`) et souscriptions push (`push_subscriptions`, US-11) sont les deux seules tables du projet avec une policy DELETE (préférences de planning réversibles / données techniques d'appareil, pas des données de combat protégées par RG-04). Édition d'un template = **futur seulement** (B4), ne touche jamais les instances déjà créées. Gestion : `/vestiaire/entrainement`. **Dette assumée MVP** : la création se fait via l'écran de gestion, pas via un toggle « récurrente » dans le champ d'ajout de l'Arène (repoussé). **Issue #156 — trois verrous anti-doublon.** Deux chemins de duplication existaient. **P1**, une course : `generateRecurringInstances()` mutait à chaque GET de `/`, en lecture-puis-écriture non atomique, et `/` est **préfetchée par le `<Link href="/">` de `BottomNav`** — un prefetch RSC exécute le composant serveur, donc la mutation ; deux exécutions concurrentes lisaient un ensemble vide et inséraient chacune la leur. **P2**, déterministe : la génération créait l'instance du jour, puis « Reporter » au Réveil ramenait le reste de la veille de la **même** routine sur `day_date = today`. Correctifs : `planRecurringGeneration` reçoit un 5ᵉ argument `overdueTemplateIds` et saute toute routine ayant un reste actif sur un jour antérieur (P2) ; un index unique **partiel** `tasks_recurring_unique_per_day` (`on (user_id, day_date, recurring_template_id) where recurring_template_id is not null and is_abandoned = false` — partiel car les doublons soldés gardent la même clé que la ligne conservée, un index plein empêcherait sa propre création) ferme P1. `profiles.last_recurring_gen_day` est un **cache de saut**, écrit **après** succès et jamais un verrou pris en amont — réserver la journée avant le travail ferait qu'un prefetch annulé consommerait la réservation sans rien créer, et la routine manquerait jusqu'au lendemain ; `createRecurringTemplate` et la relance de fin de Réveil passent `force: true` pour l'ignorer. **Piège PostgREST découvert en vérifiant en direct (pas seulement supposé)** : `.upsert(rows, { onConflict: "..." })` ne peut **pas** cibler un index partiel — PostgREST génère un `ON CONFLICT (colonnes)` sans le prédicat `WHERE` de l'index, que Postgres rejette avec `42P10` (« no unique or exclusion constraint matching the ON CONFLICT specification »). L'insertion se fait donc ligne par ligne, chaque conflit `23505` étant intercepté comme « course perdue » (no-op) plutôt qu'une vraie erreur — un insert multi-lignes unique aurait par ailleurs annulé tout le lot dès qu'UNE routine entrait en conflit, alors que chaque routine doit pouvoir réussir indépendamment des autres. Les doublons déjà en base ont été soldés par la migration `20260802120000` en `is_abandoned` (aucun DELETE, RG-04), en conservant la ligne cochée s'il y en avait une, sinon la plus ancienne. **Régénération en fin de Réveil et propagation** : une routine dont le reste traînait n'était pas générée au chargement (P2 ci-dessus) ; `WakeUpRitual` relance `generateRecurringInstances({ force: true })` une fois tous les restes soldés, et ses lignes créées empruntent le **même canal** que les restes reportés du bug #70 (`onResolved({ deferredTasks, createdTasks })`, fusionnées dans le state d'`Arena` — même raison : overlay client bloquant, `revalidatePath` n'atteint pas un state déjà hydraté).

**Rage Quit vs Annihiler (`abandon_reason`, US-15)** — Les deux posent `is_abandoned=true` (RG-04, jamais de DELETE) mais portent une **émotion opposée**, distinguée par `tasks.abandon_reason` : `rage_quit` (abandon **punitif** d'une tâche active du jour, en cours de combat → malus **−5 XP clampé sans de-level** via `applyRageQuitPenalty`, ≠ `applyXpDelta` qui peut redescendre de niveau ; punchline « le Boss ricane ») vs `annihilated` (reste nettoyé **sereinement** au Réveil, aucun malus). Le malus est appliqué **une fois par action** (rage-quit d'une racine à N enfants = −5 XP, pas −5×N) ; la cascade sur les sous-tâches actives est calculée par `collectAbandonCascade` (pur). L'**undo** (`undoRageQuit`, même jour) ne restaure que les lignes `abandon_reason='rage_quit'` et rembourse +5 XP — un « Annihiler » n'est pas annulable par ce chemin. **Perfect / K.O. en direct (US-16)** — Le déclenchement de la célébration est une **fonction pure de transition** `koOutcome(prevBossHp, nextBossHp, bossMaxHp, heroHp)` (`lib/game-engine.ts`) : `null` sauf transition→0 valide, `perfect` si Héro à 100 HP (aucun reste non résolu), sinon `ko`. **Cron push — Inngest, pas de schedule par utilisateur (US-11, refactor 2026-07-30)** — Le palier **Hobby** de Vercel (cf. **Garde de session (`proxy.ts`) — routes techniques exemptées côté anonyme uniquement (US-11)** — `proxy.ts` (Middleware Next.js, renommé depuis `middleware.ts` en Next 16) a un matcher qui couvre tout sauf les assets statiques, donc y compris `/api/*` : sans exemption, `lib/supabase/middleware.ts` redirigeait toute requête sans cookie Supabase vers `/welcome`, y compris les appels externes légitimes (Inngest sur `/api/inngest`, webhooks/OAuth). `isPublicRoute(path)` (`lib/supabase/middleware.ts`, testée dans `lib/supabase/middleware.test.ts`) exempte désormais tout `/api/*` en plus de `/login`/`/welcome`, mais **uniquement pour le garde anonyme** (`!user && !isPublicRoute`) — le garde inverse (utilisateur déjà connecté redirigé loin d'une page publique) reste volontairement restreint à `/login`/`/welcome` seuls, jamais `/api/*` : sinon un utilisateur authentifié appelant une route `/api/*` protégée par sa propre logique (ex. `/api/share-card`, US-20) serait bounced vers `/` avant même d'atteindre son handler. **L'ordre d'affichage d'une fratrie est DÉRIVÉ du contenu, jamais écrit en base (issue #195)** — `Arena.handleToggle`/`handleAdd`/`handleAddSubtask` calculaient l'ordre cible d'une fratrie au moment du clic (`planCompletionReorder`/`insertNewActiveTaskId`) puis n'appelaient `reorderSiblings(parentId, orderedTaskIds)` qu'**après** la réponse de la mutation. Toute mutation concurrente pendant la fenêtre réseau rendait ce payload périmé, avec deux modes de défaillance **silencieux** : `reorderSiblings` rejette le payload **entier** si un seul id est devenu `is_abandoned` entre-temps (l'appel étant best-effort, aucun message — la tâche reste en place) ; sinon le serveur ne renumérote **que les ids reçus**, laissant les autres membres du groupe sur leur ancienne position → **positions dupliquées**, départagées arbitrairement par Postgres puisque le tri portait sur `position` seule. La sérialisation par fratrie (`reorderQueueRef`, issue #144) garantit l'ordre d'**application**, pas la **fraîcheur** des payloads — c'est pour ça qu'elle n'avait rien corrigé. Reproduit sous latence simulée (1,5 s) en cochant deux tâches d'affilée (`pendingMutationIds`/Fix #95 ne verrouille que la tâche en vol) : `0·A 1·B 2·C 3·D` → les deux complétées remontaient **en tête**. La fenêtre étant la latence réseau, le bug était fréquent en 4G et quasi introuvable en local : d'où « régulier mais sans scénario de repro ». Dégâts mesurés en base avant correctif (données réelles) : 3 groupes à positions dupliquées (dont `[0,0,0,3,5]`) et 4 groupes violant l'invariant (dont `0· 1· 2✓ 3· 4·`).

**Le correctif dérive l'ordre au rendu** : `compareForDisplay` (`lib/game-engine.ts` — complétées après actives, puis `position`, puis `id`) est le comparateur unique de `sortTasksHierarchically` **et** de `planReorder` ; cocher une tâche suffit à la faire descendre, **zéro écriture**, donc plus aucun ordre à transporter ni à périmer. `ReorderableTask`/`HierarchyTask` portent `is_completed` pour cette raison : sans lui, un drag & drop calculerait sa cible sur un ordre que l'utilisateur ne voit pas dès qu'une complétée garde une position basse. **Une première version du correctif renumérotait le groupe côté serveur** (`normalizeSiblingPositions` appelée par les 8 actions qui changent la composition d'un groupe) : fonctionnellement correcte et validée par les mêmes tests, mais **mesurée trop coûteuse et abandonnée** — cocher la première tâche d'une liste de 20 décale les 20 lignes, soit 20 `UPDATE` séquentiels, et une boucle qui coche tout devient quadratique (`e2e/ko-overlay-viewport.spec.ts` : 1,8 min → 2,7 min ; suite e2e complète × 2). Ne pas la réintroduire pour « nettoyer les positions » : le tri dérivé rend ce nettoyage inutile, et le départage explicite sur l'`id` à position égale existe précisément pour que les positions dupliquées **déjà en base** s'affichent dans un ordre stable d'un chargement à l'autre. `reorderSiblings` **reste**, réservé au drag & drop — le seul cas où l'ordre est explicitement voulu par l'utilisateur et non dérivable ; il réécrit 0..N sur l'ordre affiché, ce qui nettoie au passage les positions du groupe dragué. L'ancien mécanisme a été **supprimé** (`planCompletionReorder`, `reorderAfterCompletionToggle`, `insertNewActiveTaskId`, `insertAfterLastActive` + tests, ~111 lignes) plutôt que laissé à côté du nouveau : deux systèmes d'ordre concurrents rejoueraient la classe de bug corrigée. Effets de bord assumés : l'ordre **entre complétées** dérive de leurs positions et non de l'heure de complétion (aucune colonne `completed_at`) ; et une tâche que l'utilisateur a draguée manuellement au-dessus d'une complétée redescendra sous elle (l'ancien `insertAfterLastActive` préservait ce cas, le tri dérivé non — l'invariant « complétées en bas » l'emporte désormais). **Corrigeait aussi un trou jamais vu** : `insertTaskForUser` est partagé par le webhook Siri (US-03) et le serveur MCP de Gemini (US-22), qui n'ont aucun client pour réordonner — une tâche dictée atterrissait donc **toujours** sous les complétées ; elle s'affiche maintenant au bon endroit sans que ces chemins aient à changer d'une ligne.

**Piège de test associé** : `e2e/task-ordering.spec.ts` asserte l'ordre du **DOM** (`li[id^="task-"]`), jamais la colonne `position` — depuis ce correctif, `position` ne porte plus l'invariant. Deux conditions sans lesquelles ces tests passeraient même avec le bug : (1) la latence simulée sur les server actions (`page.route`, 1,5 s), la fenêtre de course **étant** la latence réseau ; (2) attendre la **base** (et non `networkidle`) avant tout `page.reload()` — sous latence, `networkidle` peut se résoudre entre le retour du premier POST et l'émission du second (Playwright attend d'abord que la ligne visée soit stable, or la liste se réordonne au premier clic), et le reload annule alors la requête en vol : on testerait l'annulation, pas la persistance. **Aucune API navigateur dans le rendu initial d'un composant client — `useSyncExternalStore`, jamais un initialiseur de `useState` (issue #194)** — Un composant `"use client"` est **aussi rendu sur le serveur** avant hydratation : tout `useState(() => …)` qui lit `window`/`Notification`/`matchMedia`/`new Date()` produit une valeur serveur différente de la valeur client, donc un mismatch d'hydratation React (#418). Conséquence bien pire qu'un warning : React **régénère tout l'arbre client** et **abandonne le replay des évènements discrets** capturés pendant l'hydratation — un clic parti juste après l'affichage est perdu **sans aucune trace** (ni erreur UI, ni log applicatif). C'était la cause du rouge déterministe de `e2e/volume-interieur.spec.ts` (« le clic sur Brut ne fait rien »), diagnostiqué à tort comme un bug de la server action puis comme un flake. Trois occurrences trouvées et corrigées, toutes sur le même patron : `PushReminderToggle` (lisait `Notification.permission` → `"unsupported"` côté serveur, donc un `<p>` « indisponible » là où le client rendait le `<div>` du toggle), `MidnightTimer` (formatait le temps restant avec l'horloge **et le fuseau du serveur** — UTC sur Vercel — donc un texte différent à chaque chargement hors UTC), `Arena` (`matchMedia("(prefers-reduced-motion: reduce)")` → toujours `false` côté serveur, donc la classe `sprite-run` et les styles d'animation divergeaient pour tout utilisateur en reduced-motion). Le patron correct était déjà dans le repo (`hooks/useBrowserTimezone.ts`, `hooks/useSpeechToText.ts`) : `useSyncExternalStore` avec un `getServerSnapshot` qui renvoie une valeur **neutre** (placeholder `--:--`, statut `"pending"`, `false`) — React rend avec ce snapshot pendant l'hydratation (sortie identique au HTML serveur), puis re-rend avec la valeur client juste après, **sans erreur**. Nouveau `hooks/usePrefersReducedMotion.ts` (seul des trois avec une vraie souscription : l'utilisateur peut basculer le réglage système sans recharger). **Méthode de diagnostic à reprendre** : le message prod est minifié (`Minified React error #418; …args[]=HTML`) et ne dit pas *où* ; relancer en `next dev` et capturer `page.on("pageerror")` **en entier** donne l'arbre de composants avec la ligne `+`/`-` exacte du nœud fautif. Piège dans le piège : ce message est **multi-lignes**, un `grep` sur la sortie n'en montre que la première ligne et fait croire à un message tronqué sans diff. **Ce que les tests unitaires ne peuvent pas prouver ici** : jsdom ne distingue pas rendu serveur et rendu client, il ne reproduit donc aucun de ces mismatches — `e2e/hydration.spec.ts` (assertion « zéro erreur d'hydratation » sur `/vestiaire/profil` et `/`) est la seule vraie garde, et l'`Arena` en particulier n'est rouge qu'avec `reducedMotion: "reduce"` (forcé pour toute la suite par `playwright.config.ts`) — en local, `MidnightTimer` ne peut de toute façon pas mentir puisque le serveur de test partage le fuseau du navigateur, contrairement à la prod.

Symptôme trompeur côté UI : `CharacterSelect.confirmPurchase` traite `res.error === null` comme un succès, donc aucun message d'erreur, la modale se ferme, `ownedIds` inchangé → « le clic ne fait rien », signature typique d'un bug de front alors que la cause est un `return` anticipé côté serveur. **Le même garde sur `purchaseSkin` (`if (skin.isDefault) return { error: null }`) est en revanche correct et doit rester** : `isSkinOwned` renvoie toujours `true` pour `<hero>_default` (aucune ligne en base, gratuite dès que le héros est possédé, D4 du spec US-53), l'UI ne propose donc jamais son achat. `app/actions/shop.test.ts` (créé à cette occasion — aucun test n'existait sur ces server actions) verrouille l'achat de **chaque** héros du catalogue et de **chaque** tenue alternative via `it.each` sur `HEROES`/`SKINS`, plutôt qu'un cas `fire_knight` en dur : un futur héros marqué `isDefault` ne peut plus redevenir silencieusement inachetable. Règle générale : tout drapeau de catalogue (`isDefault`) dont la sémantique de possession a migré vers la base est à re-auditer chez **tous** ses consommateurs, jamais seulement là où le changement a été écrit — l'aucun-effet silencieux est le mode d'échec le plus coûteux à diagnostiquer (aucune trace, aucun log, aucune erreur).

**État "verrouillé" au Marché Noir : `grayscale` complet efface la teinte, `saturate` partiel la préserve (issue #169)** — `CharacterSelect.tsx` dégrade visuellement les héros/tenues non possédés via un filtre CSS inline. Pour la grille héros (portraits pixel-art sur `bg-black/40`), `grayscale(1) brightness(0.85)` garde la silhouette lisible sans donner d'info couleur à cacher — légitime, la forme prime sur la teinte pour un portrait à débloquer. Pour la bande de swatches de tenues (`backgroundColor: skin.swatchColor`), un `grayscale(1)` complet est un contre-sens : la teinte du catalogue est la **seule** information qui distingue deux tenues verrouillées entre elles, et le griser efface exactement ce qui devait rester lisible (deux swatches à luminosité proche mais teinte différente deviennent visuellement identiques). Le filtre retenu pour tout élément coloré (pas un portrait) qui doit rester "verrouillé mais distinguable" est `saturate(x) brightness(y)`, jamais `grayscale`. Aucun nouveau token DESIGN.md — ajustement des paramètres de filtre déjà en place, pas de nouvelle couleur hors palette.

**Migrations Supabase hors-ordre : `supabase db push` les ignore sans le signaler comme un blocage durable (bug prod #70)** — Deux migrations (`20260723110000_create_oauth_mcp.sql`, `20260723130000_add_profile_aggressivity_level.sql`) sont restées **non appliquées en production** pendant plusieurs jours, cause racine de 3 bugs simultanés (onboarding et Volume Intérieur du Vestiaire en échec sur `profiles.aggressivity_level` inexistante ; Gemini ne pouvait jamais s'auto-enregistrer faute de table `oauth_clients`). Cause : `20260723110000` porte un timestamp **antérieur** à des migrations déjà appliquées (`20260723120000`/`20260723120100`) — `supabase db push --linked` refuse alors de l'insérer par défaut (« Found local migration files to be inserted before the last migration on remote database ») et exige `--include-all`. Ce refus est une erreur explicite en sortie de commande, mais **rien ne le fait remonter automatiquement** (pas de check CI, pas de hook `predeploy`) : une fois vu une fois et non traité, il repasse inaperçu indéfiniment. `npx supabase migration list --linked` (colonnes Local vs Remote) est la commande de vérité pour détecter un écart — **à lancer avant de merger toute PR qui ajoute un fichier dans `supabase/migrations/`**, en plus du build/tests locaux déjà obligatoires (cf. Workflow Git). Toujours nommer les migrations avec un timestamp strictement postérieur à la dernière migration existante sur `main` au moment de la création du fichier, pas au moment du merge (un rebase peut réordonner l'historique de fichiers sans réordonner leurs timestamps).

**Le Réveil (`WakeUpRitual`) : overlay client qui ne déclenche jamais de refetch — toute donnée modifiée pendant le rituel doit être remontée explicitement (bug prod #70)** — `WakeUpRitual` mute la base via des server actions (`deferOverdueTask`, `deferAllOverdue`, `completeOverdueTask`, `annihilateOverdueTask`…) puis, une fois tous les restes traités, appelle `onResolved()` qui ne faisait que `setShowWakeUp(false)` côté `Arena.tsx` — jamais de `router.refresh()` ni de re-fetch. `Arena.tsx` garde son propre state `tasks` initialisé une seule fois depuis les props serveur (`initialTasks`, capturées **avant** l'ouverture du rituel) : une tâche reportée ("Reporter") était donc correctement ramenée au jour courant en base, mais invisible dans l'Arène jusqu'au prochain rechargement complet — un effet visuellement indiscernable d'un "Annihiler". `revalidatePath("/")` (appelé côté serveur par ces actions) invalide le cache de route Next.js mais ne pousse aucune donnée vers un composant client déjà monté sans navigation. Correctif : `deferOverdueTask`/`deferAllOverdue` renvoient désormais les lignes mises à jour (`TaskActionResult.deferredTasks`) ; `WakeUpRitual` les accumule (`useRef`, pas besoin de re-render dessus) et les passe à `onResolved(deferredTasks)` ; `Arena.tsx` les fusionne dans son state (`setTasks(prev => [...prev, ...deferredTasks])`). Règle générale : toute mutation faite **à l'intérieur** d'un overlay client bloquant qui doit rester visible après sa fermeture doit soit renvoyer les lignes affectées pour fusion explicite côté parent, soit déclencher un `router.refresh()` — `revalidatePath` seul ne suffit jamais pour un state client déjà hydraté. **Issue #156** applique la même règle à la régénération des routines relancée en fin de Réveil (voir l'entrée « Mode Entraînement » ci-dessus pour le détail) : `onResolved` passe désormais `{ deferredTasks, createdTasks }` plutôt qu'un simple tableau.

**Navigation : `BottomNav` partout, `BackLink` seulement pour remonter d'un niveau (audit UX 2026-07-24)** — `components/ui/BottomNav.tsx` (3 onglets Arène/Vestiaire/Marché Noir) est monté sur **tous** les écrans authentifiés, pas seulement l'Arène : Le Vestiaire, Tableau de Chasse, Le Guide (index + article), Mes Routines passent `active="vestiaire"` (ils sont tous atteints depuis Le Vestiaire, aucun onglet dédié) ; Le Marché Noir passe `active="marche-noir"`. **Flake e2e « utilisateur test introuvable » — root cause confirmée : JWT Admin GoTrue rejeté sous concurrence, guéri par retry (`listUsersRetrying`/`deleteUserRetrying`, `e2e/fixtures.ts`)** — la piste documentée le 2026-07-24 (JWT ES256 `kid <nil>` intermittent) est désormais **reproduite à la demande** : 20 appels séquentiels à `admin.auth.admin.listUsers()` passent systématiquement, mais une rafale de 10 appels concurrents en déclenche systématiquement une partie en échec (403 `bad_jwt`), et **un retry immédiat guérit 100% des échecs observés** (8/8 sur rafale répétée) — confirme qu'il s'agit d'un flake d'infra externe (projet Supabase lié), jamais d'un bug de code ou d'ordre d'exécution des specs. **dnd-kit : capture de pointeur résiduelle après un drag simulé Playwright — un clic ultérieur peut se perdre silencieusement (`e2e/nesting-dnd.spec.ts`)** — flake observé uniquement en run complet (jamais en isolation, ni via bump du timeout du hook à 60s — écarté comme piste, cf. historique) : le bouton « × » (Abandonner) de la tâche traitée juste après un drag reste marqué `:active` en snapshot Playwright sans jamais ouvrir sa modale de confirmation (`role="alertdialog"` absent du DOM). `PointerSensor` de dnd-kit appelle `setPointerCapture()` sur `pointerdown` pour suivre le drag au-delà des bornes de l'élément ; la séquence `mouse.down()` → deux `mouse.move()` → `mouse.up()` de `dragOnto` ne dispatche aucun `pointermove` **après** le `mouseup`, et dans certains runs la capture reste résiduelle côté navigateur — un clic suivant sur un autre bouton est alors livré à l'élément qui détenait la capture plutôt qu'à sa cible réelle. Correctif : un `page.mouse.move()` supplémentaire juste après `mouse.up()` dans `dragOnto` (`e2e/nesting-dnd.spec.ts`), forçant la relâche complète — validé sur 3 runs complets consécutifs (0 échec) après l'avoir reproduit une fois sans lui. Si ce flake réapparaît sur un **autre** test drag & drop, appliquer le même correctif plutôt que de bump un timeout (déjà tenté, sans effet — la modale ne s'ouvrait pas du tout, ce n'était pas un problème de marge).

**Auto-reorder à l'ajout (issue #111) : exclure les tâches abandonnées du pool, rollback jamais sur une fermeture stale** — `handleAdd`/`handleAddSubtask` (`Arena.tsx`) appellent `reorderSiblingsAction` quand des racines/sous-tâches sont déjà complétées, pour insérer la nouvelle tâche juste au-dessus. **Assertions e2e sur un état d'animation transitoire : échantillonner, jamais poller — et surtout jamais garder une référence de nœud, `Arena` remonte toute la scène à chaque `pulse`** — `combat-animations.spec.ts` enchaînait `await expect(boss).toHaveAttribute("data-anim-state", "attack")` puis `await expect(hero).toHaveAttribute("data-anim-state", "hurt")`. Le `hurt` ne dure que 350 ms (`HURT_DURATION_MS`) et ne démarre qu'à la frame d'impact de l'attaque du Boss (~40 % d'une anim de 600-800 ms). Le poll de `expect` recule (100 ms → 250 → 500 → 1000 ms), donc passé la première seconde il rate régulièrement un état qui n'apparaît **qu'une fois** : flake CI avec 14 résolutions consécutives à "idle", reproduit en local en mode CI avec 33 résolutions sur 15 s. Ce n'est pas un problème de marge — allonger le timeout ne change rien, il faut arrêter d'échantillonner au poll. Correctif : une boucle `requestAnimationFrame` posée par `page.evaluate` avant le déclencheur, qui enregistre la **suite** des `data-anim-state` (~16 ms de résolution), puis assertion sur cet historique. Bénéfice au passage : le « jamais attack » du nom du test devient une assertion réelle au lieu d'être déduit.

⚠️ **Deux fausses pistes traversées, à ne pas refaire.** (1) Armer les deux `expect(...)` avant le déclencheur puis `Promise.all` — **empire** le problème : les polls commencent plus tôt, donc leur intervalle a déjà reculé à 500-1000 ms quand la fenêtre arrive. (2) Un `MutationObserver` attaché aux deux nœuds `[data-testid="character-sprite"]` — **ne remonte rien du tout** : `Arena.tsx` re-keye le bloc contenant `VersusScene` (`key={pulse ? \`fx-${pulse.key}\` : "fx-idle"}`) et toute action qui change les HP change `pulse`, donc React **remonte la scène entière au moment même du déclencheur** ; les nœuds observés sont détachés et l'observateur devient orphelin. Symptôme trompeur : `{heroHurt: false, bossAttack: false}` — un faux négatif sur les DEUX personnages, qu'on peut lire à tort comme « la contre-attaque n'a pas lieu », alors que c'est l'instrumentation qui est aveugle. Règle générale : dans l'Arène, ne jamais mémoriser une référence de nœud DOM (ni observateur attaché) à travers une mutation de HP — re-résoudre le sélecteur à chaque échantillon.

**`outline-none` inconditionnel + `focus-visible:outline*` sur le même élément : le focus clavier devient invisible, pas juste "moins visible" (audit Impeccable, issue #189)** — Trouvé sur `AddTaskForm.tsx`/`SubtaskForm.tsx` : la classe combinait `outline-none` (posé sans condition) avec `focus-visible:outline focus-visible:outline-2 focus-visible:outline-xp focus-visible:outline-offset-2`. Les deux utilitaires ciblent la même propriété CSS `outline` — l'état "au repos" (`outline-none`, toujours actif) gagne, et la variante `focus-visible:outline*` ne s'applique jamais, même quand `:focus-visible` matche réellement. Confirmé par `getComputedStyle` (`outlineStyle` reste `"none"`) et par capture d'écran (curseur actif dans le champ, aucun ring visible) — pas une supposition. Le champ concerné (`AddTaskForm`, "Balance ta tâche…") est l'interaction la plus fréquente de toute l'app : un utilisateur au clavier ne pouvait pas savoir qu'il l'avait atteint. **Le pattern qui fonctionne déjà ailleurs dans ce repo** (`/login`, `/welcome`, l'onboarding) est `outline-none focus-visible:ring-2 focus-visible:ring-xp` — `ring` utilise `box-shadow`, une propriété différente d'`outline`, donc insensible à ce conflit. Toujours préférer `ring` à `outline` quand un `outline-none` de repos coexiste avec un état focus-visible sur le même élément. **Piège de contraste voisin, même famille de composants, cause différente** : `BossBar.tsx`/`HeroBar.tsx`/`TitleSelector.tsx` utilisaient `focus-visible:outline-none focus-visible:ring-1 focus-visible:ring-hp/20` — ce pattern-là fonctionne techniquement (le `ring` s'affiche bel et bien), mais à 20% d'opacité le contraste mesuré tombe à ~1.5:1 contre `surface` (WCAG 1.4.11 exige 3:1) — recalculé depuis les tokens OKLCH bruts (conversion Oklab → sRGB linéaire → luminance relative), pas estimé à l'œil. Passé à `ring-2 ring-hp` (pleine opacité, 3.40:1 mesuré contre `surface`) sur les trois. Un anneau de focus qui *s'affiche* n'est pas la même preuve qu'un anneau de focus *suffisamment contrasté* — vérifier les deux séparément avant de clore un constat d'accessibilité.

**Couche domaine `lib/domain/` — client Supabase et userId explicites, jamais de session cookie (issue #201)** — Toute la logique métier des tâches, de la boutique, du boss et de la progression vit sous `lib/domain/`, en fonctions `(supabase: SupabaseClient, userId: string, …)`. Les server actions de `app/actions/` ne font plus que trois gestes : résoudre la session, appeler le domaine, traduire le code d'erreur en copy « voix » puis `revalidatePath`. **Trois interdits sous `lib/domain/`** : `"use server"`, `revalidatePath`, `supabase.auth.getUser()` — un seul suffit à rendre la fonction inappelable depuis le serveur MCP ou le webhook Siri, qui n'ont aucun cookie. Le client est **toujours** typé `SupabaseClient` de `@supabase/supabase-js`, jamais `ReturnType<typeof createClient>` : cet alias fait perdre l'inférence sur `.insert()`, qui résout vers `never[]` et casse `tsc --noEmit` dès qu'un client traverse une frontière de fonction (`app/actions/achievements.ts` portait ce défaut latent, invisible tant qu'aucun client service-role ne lui était passé). Le domaine renvoie des **codes** (`DomainErrorCode`, `lib/domain/errors.ts`), jamais de français : le MCP les sert tels quels à un agent, l'UI les habille.

**Scopes OAuth du serveur MCP — défaut restrictif, refus explicite sur l'inconnu (issue #201)** — `lib/oauth-scopes.ts` définit 4 scopes (`tasks:read`/`tasks:write`/`profile:read`/`profile:write`). Une requête `/oauth/authorize` sans paramètre `scope` accorde `tasks:read tasks:write` — jamais `profile:write` : un client qui ne demande rien n'obtient pas le droit de changer l'équipement. Un scope inconnu est refusé (page d'erreur), jamais filtré silencieusement. `lib/mcp-tools.ts` (registry de tools) filtre `tools/list` selon le scope du token — un agent ne voit que ce qu'il peut appeler. Le rate limit (`lib/mcp-rate-limit.ts`, RPC `consume_mcp_quota`) vit dans une table dédiée (`mcp_rate_limit`) et non sur `oauth_tokens`, qui est vidée à chaque rotation de refresh token (`handleRefreshTokenGrant`) — un compteur qui y vivrait serait effacé par un simple refresh. **`consume_mcp_quota` est la première fonction SQL de ce type dans le repo, et son hygiène de droits ne se devine pas** : sur un projet Supabase hébergé, `revoke execute ... from public` ne retire QUE le grant PUBLIC implicite — le bootstrap Supabase pose par défaut `alter default privileges for role postgres in schema public grant all on functions to postgres, anon, authenticated, service_role`, et comme les migrations s'exécutent en tant que `postgres` dans `public`, `anon`/`authenticated` reçoivent au `CREATE FUNCTION` un grant EXECUTE explicite que le revoke ne touche pas — n'importe qui muni de la clé anon pourrait alors appeler le RPC via PostgREST (`POST /rest/v1/rpc/consume_mcp_quota`) et épuiser le quota d'un autre utilisateur. Le correctif nomme les rôles explicitement (`revoke ... from public, anon, authenticated`) — toute future fonction `security definer` doit copier ce bloc complet, pas seulement le `revoke from public`. Corollaire : `consume_mcp_quota` est passée en **security invoker** (pas definer) — `mcp_rate_limit` a RLS activé sans aucune policy, et `service_role` (seul appelant légitime, `/api/mcp`) a `BYPASSRLS`, donc un appel invoker fonctionne à l'identique pour lui tout en faisant échouer sur RLS un appel `anon`/`authenticated` égaré plutôt que de muter la ligne d'une victime — ce pattern élimine la classe de bug plutôt que de la rustiner. **`consumeMcpQuota` (le wrapper TS) échoue délibérément ouvert sur une erreur RPC** (`if (error) return true`) : le rate limit protège contre l'abus, il ne doit jamais devenir un point de défaillance unique qui bloque un appel MCP légitime si la migration n'est pas encore appliquée (ou la table absente) — même philosophie fail-open que le rate limit IP best-effort de `lib/rate-limit.ts`.

**Tools MCP de lecture — jamais d'effet de bord, et le faux client filtre enfin (issue #201, lot 3)** — Les 5 tools de lecture (`list_tasks`, `get_boss_status`, `get_streak`, `get_progression`, `list_heroes`) délèguent tous à `lib/domain/`, jamais à une server action. `get_boss_status` appelle `readDailyBoss` et **jamais** `resolveDailyBoss` : ce dernier upsert `daily_boss` et évalue les succès, donc un agent qui consulte le Boss à 3h du matin figerait le tirage du jour et débloquerait des succès sans que l'utilisateur ait ouvert l'app (D6.1 du spec). Un boss non encore tiré renvoie un message explicite, pas une erreur. **Corollaire de sécurité posé par ce lot** : `FakeQueryBuilder` (`lib/domain/fake-supabase.ts`) filtre désormais réellement sur `eq`/`in`/`lt`/`is` — avant, tous étaient des no-op, donc aucun test du domaine ne pouvait détecter un `.eq("user_id", …)` manquant. C'était sans conséquence tant que RLS protégeait un client cookie-scope, mais le serveur MCP appelle le domaine avec un client **service-role qui contourne RLS** : ces filtres applicatifs sont la seule frontière de tenant qui reste. `lib/domain/tenant-isolation.test.ts` verrouille l'invariant. **Correction (lot 4, cf. entrée dédiée ci-dessous) : `or()` n'est plus un no-op** — l'affirmation ci-dessus, correcte au moment du lot 3, a été explicitement repoussée par le lot 4, qui a fait filtrer `or()` en plus de `select(cols, { count, head })`. **Ce filtrage a immédiatement trouvé une vraie fuite cross-tenant, invisible à tous les tests jusque-là** : dans `setTaskDeadlineForUser`, l'UPDATE lui-même était déjà correctement scopé (`.eq("id", taskId).eq("user_id", userId)`) — la fuite venait d'ailleurs. Le `select` de relecture qui suit (`.select("reminder_enabled, reminder_offset_minutes").eq("id", taskId)`) n'avait lui aucun filtre `user_id` et lisait donc les réglages de rappel d'un **autre** utilisateur ; pire, les effets de bord (`cancelDeadlineReminder`/`scheduleDeadlineReminder`) s'exécutaient **même quand l'update correctement scopé n'avait matché aucune ligne** (le résultat n'était vérifié que sur `error`, jamais sur le nombre de lignes touchées), annulant le rappel Inngest d'un autre utilisateur tout en renvoyant `error: null` — un faux succès silencieux. La vraie leçon n'est donc pas « vérifier ses UPDATE » : c'est qu'**une écriture correctement scopée, suivie d'une lecture non scopée ou d'un effet de bord inconditionnel, fuite quand même — et rapporte un succès en le faisant**. Corrigé dans ce lot en ajoutant `.select("id")` à l'UPDATE et en court-circuitant sur zéro ligne mise à jour **avant** même le branchement sur `deadlineAt === null`, plutôt qu'en se contentant d'ajouter un filtre à la lecture aval ; c'est aussi la justification concrète de l'ordre imposé par le plan (le fix du faux client devait précéder toute fonction de lecture, sinon ce bug serait resté invisible une fois de plus). **Second piège trouvé en écrivant `listTasksForUser`** : avec `include_completed: false`, une tâche parent peut être exclue du résultat alors qu'une de ses sous-tâches reste active et visible — la sous-tâche renvoyée doit alors avoir son `parentId` mis à `null`, sinon elle porterait une référence vers une tâche absente de l'ensemble renvoyé, et le handler MCP (qui indente sur `parentId`) rendrait une sous-tâche orpheline indentée sous rien.

**Tools MCP d'écriture — catalogue à 10 tools, discipline `undefined` vs `null`, et le dernier no-op du faux client comblé (issue #201, lot 4)** — `TOOL_REGISTRY` (`lib/mcp-tools.ts`) passe de 6 à 10 entrées : `add_task` (étendu avec `parent_id`/`day`), `complete_task`, `set_deadline`, `move_task`, `equip_hero` s'ajoutent aux 5 lectures du lot 3. Scopes : les quatre premiers `tasks:write` (`add_task`/`complete_task`/`set_deadline`/`move_task`), `equip_hero` seul `profile:write` — il ne touche aucune tâche. **`parseArgs` renomme les clés** : le handler lit les clés produites par le parseur (`includeCompleted`, `taskId`…), jamais les noms de propriété de `inputSchema` (`include_completed`, `task_id`) — se tromper renvoie `undefined` silencieusement, sans erreur nulle part, puisque TypeScript ne peut rien vérifier sur un `Record<string, unknown>` indexé par des clés arbitraires. **`add_task` avec `parent_id` ET `day` en même temps est refusé, jamais ignoré** : une sous-tâche hérite du `day_date` de sa tâche parente (issue #116), le tool ne peut donc structurellement pas honorer `day` sur une sous-tâche — renvoyer `error: null` avec une tâche datée autrement que demandé est le mode d'échec silencieux que ce projet a déjà payé deux fois (`purchaseHero` #192, `setTaskDeadlineForUser` lot 3). **`setTaskDeadlineForUser` : ses deux paramètres de rappel optionnels utilisent `undefined` pour dire « ne touche pas la colonne »** — un parseur qui coerce avec `=== true` (comme celui de `complete_task`, où c'est correct) transformerait "argument non fourni" en "désactive le rappel" sur `set_deadline`, et TypeScript ne l'attrape pas (les deux formes typent `boolean`). **Les filtres du faux client Supabase sont une infrastructure de sécurité, pas du sucre de test** : `or()` (ce lot) et `select(cols, { count, head })` (ce lot) rejoignent `eq`/`in`/`lt`/`is` (lot 3) parmi les filtres qui filtrent réellement désormais — chaque no-op rendait toute une classe de filtre `user_id` manquant intestable, sans conséquence tant que RLS protégeait un client cookie-scope mais critique dès qu'un client service-role (le serveur MCP) contourne RLS. Les 8 requêtes d'`assembleAchievementContext` (`lib/domain/achievements.ts`) sont maintenant verrouillées par `lib/domain/tenant-isolation.test.ts` — pas onze : ce chiffre, écrit initialement dans ce lot, incluait par erreur les requêtes propres d'`applyNewAchievements` (lecture/écriture de `unlocked_achievements`), qui n'en font pas partie. **Une convention d'erreur pour tout le fichier** : `<code machine> : <phrase courte>`, dérivée d'un `Record<DomainErrorCode, string>` exhaustif — cette exhaustivité a exposé `"insert_task_failed"`, une chaîne qui ressemblait à un code sans jamais avoir été membre de l'union `DomainErrorCode`. **Une écriture correctement scopée, suivie d'une inférence que l'appelant n'a pas la légitimité de faire, reste un bug** (même famille que la fuite `setTaskDeadlineForUser` du lot 3) : `move_task` route vers `reportToTomorrowForUser`/`bringToTodayForUser`, dont l'UPDATE combine jusqu'à cinq filtres conjonctifs (tenant + `day_date`/`is_completed`/`is_abandoned`) — 0 ligne affectée ne veut donc pas forcément dire "tâche introuvable" : déplacer une tâche déjà déplacée, ou une tâche que `list_tasks` vient de montrer comme terminée, matchait aussi 0 ligne et renvoyait `task_not_found` à tort. Le garde vit dans le domaine (une relecture ciblée sur `id`+`user_id` seuls y discrimine `task_not_found`/`task_abandoned`/`task_completed`/succès no-op) — la couche tool ne peut structurellement pas calculer cette distinction, elle ne voit que le résultat de l'UPDATE.

**Tools MCP d'écriture — 4 correctifs de revue avant PR : deux comportements, deux fuites tenant (issue #201, lot 4 revue)** — `bringToTodayForUser` (`lib/domain/tasks.ts`) portait un `.neq("day_date", today)` manquant : une tâche **déjà** sur aujourd'hui rematchait quand même l'UPDATE de `move_task { to: "today" }` et perdait silencieusement sa deadline (`deadline_at: null`) et sa position, tout en renvoyant un faux succès — `to: "today"` n'était donc pas idempotent, contrairement à `to: "tomorrow"` (lot 4). Avec le `.neq` posé, un agent qui pose une deadline puis rappelle `move_task { to: "today" }` "pour être sûr" ne la détruit plus : 0 ligne affectée bascule en succès no-op explicite (« Cette tâche est déjà sur aujourd'hui »), même patron que le no-op `to: "tomorrow"`. **`add_task { day: "tomorrow" }` annonçait un « Boss à X/Y HP » non qualifié** : ces HP sont calculés sur les tâches de **demain** (`insertTaskForUser`), jamais sur le Boss du jour courant (invariant déjà documenté ci-dessus pour "Planifier demain") — un agent qui relaie ce texte tel quel mentirait sur l'état réel du Boss. `buildAddTaskToolResult` (`lib/mcp-protocol.ts`) prend un 2ᵉ paramètre `isTomorrow` qui bascule le libellé en « Boss de demain à X/Y HP ». **Deux fuites tenant supplémentaires**, même famille que celles déjà documentées ci-dessus (lot 3/4) : `addSubtaskForUser` lisait la fratrie (pour calculer la position) sans `.eq("user_id", userId)` — une fratrie appartenant à un autre utilisateur (même `parent_id`, aucune FK ne garantit le partage de `user_id`) faussait `nextSiblingPosition` ; et `equipHeroForUser` (`lib/domain/shop.ts`) n'avait aucun garde sur le nombre de lignes réellement mises à jour par l'UPDATE `profiles` — un `userId` sans ligne `profiles` recevait un succès silencieux pour une écriture qui n'avait rien changé (même forme de faux succès que `setTaskDeadlineForUser`, lot 3). Les deux portent désormais `.select("id")` + garde sur `updatedRows.length`, verrouillés par deux tests dédiés dans `lib/domain/tenant-isolation.test.ts`.

**Tools MCP d'écriture — upsert du faux client, id d'`add_task`, convention d'erreur au niveau route, coercions de `parseListTasksArgs` (issue #201, lot 4 revue finale)** — `FakeQueryBuilder` n'avait **aucune** méthode `upsert` : son unique consommateur (`applyNewAchievements`) plantait en `TypeError` dès qu'un test faisait réellement débloquer un succès, et le test tenant existant sur cette fonction était **vacueux par construction** (contexte neutre → `evaluateAchievements` renvoie `[]` quel que soit `alreadyUnlocked` → la fonction retourne avant que l'upsert ne s'exécute jamais ; retirer le `.eq("user_id", userId)` de sa lecture gardait donc ce test au vert). `upsert()` matche désormais réellement sur les colonnes `onConflict`, et le test a été réécrit avec un contexte qui débloque `LEVEL_10` pour de vrai — preuve empirique que l'onConflict `(user_id, code)` ne fusionne jamais sur la ligne d'un autre utilisateur partageant le même `code`. **`add_task` renvoie enfin l'id de la tâche créée** dans son texte (`"Tache ajoutee (id <uuid>) pour le ..."`, même patron que la branche sous-tâche qui le faisait déjà) — avant, un agent devait rappeler `list_tasks` et regex-scraper son texte pour obtenir l'id nécessaire à tout `complete_task`/`set_deadline`/`move_task` qui suit. **La convention d'erreur `<code> : <phrase>` (posée lot 4 dans `lib/mcp-tools.ts`) s'étend à `app/api/mcp/route.ts`** : le refus de scope (`scope_denied : ...`) et le `catch` générique du handler (`internal_error : ...`) émettaient jusque-là une prose sans code ou un code nu — ni l'un ni l'autre n'est ajouté à `DomainErrorCode` (ce ne sont pas des erreurs du domaine), seule la forme de surface est unifiée. **`parseListTasksArgs` coercait encore silencieusement** : `args.day ?? "today"` collapsait `day: null` sur le défaut exactement comme une absence d'argument (contrairement à `parseAddTaskArgs`, qui refuse déjà ce cas) ; et `include_completed` gardait le pattern outlawed par `parseCompleteTaskArgs` (lot 4) — tout ce qui n'est ni `true`/`"true"` ni `false`/`"false"` (`0`, `"no"`, `{}`) retombait sur `false`. Les deux refusent désormais explicitement un type incorrect, même discipline que le reste du fichier.

**Enregistrement dynamique de client MCP : n’accepter que https + loopback IPv4 rend le serveur inutilisable par tout client natif (issue #201)** — le durcissement de l’audit #67 (PR5) visait `javascript:`/`data:` et a sur-corrigé : `isValidRedirectUri` (`lib/oauth-client-registration.ts`) n’autorisait plus que `https:` et `http:` sur `127.0.0.1`/`localhost`. Or **RFC 8252, citée par ce même durcissement, décrit trois formes de redirection** pour un client natif : §7.1 schéma privé (`monapp:/callback`), §7.2 https revendiqué, §7.3 loopback — et précise que le loopback **doit** couvrir `127.0.0.1` **et** `[::1]`. Seules §7.2 et une moitié de §7.3 passaient. Constaté en branchant un vrai client MCP le 2026-09-07 : `400 invalid_client_metadata` à l’enregistrement, donc **aucun client natif ne pouvait se connecter** — le cas d’usage même pour lequel le serveur existe. Piege de parsing associé : `new URL("http://[::1]:8080/cb").hostname` vaut `"[::1]"`, **crochets compris** — comparer à `"::1"` ne matche jamais. La sécurité ne reposait de toute façon pas sur ce filtre : `app/oauth/authorize/route.ts:63` refuse tout `redirect_uri` absent de la liste enregistrée du client (prévention d’open redirect, US-22), et l’utilisateur doit consentir — ce filtre-ci n’a qu’à écarter les schémas qui ne sont jamais une redirection (liste noire `javascript:`/`data:`/`vbscript:`/`file:`/`blob:`, conservée). **Leçon transposable** : durcir une validation en citant une RFC sans implémenter toutes ses branches produit un refus conforme en apparence et bloquant en pratique ; et un message d’erreur qui ne nomme pas la valeur refusée rend l’incompatibilité indiagnosticable des deux côtés (le corps de `/oauth/register` n’est pas journalisé non plus). Le message inclut désormais l’URI fautive. **Suite immédiate, même jour** : le message amélioré a révélé que le client s’annonçait sur `http://192.168.1.212:9119/...`, une **IP de LAN privée en clair** — ni loopback, ni schéma privé, donc un refus cette fois conforme au spec (OAuth 2.1 exige HTTPS hors loopback, et l’exception §7.3 ne couvre que `127.0.0.1`/`[::1]` précisément parce que ce trafic ne quitte pas la machine). **Écart assumé décidé par l’utilisateur** : `isLoopbackOrPrivateHost` accepte désormais les plages RFC 1918 (`10/8`, `172.16/12`, `192.168/16`) et RFC 4193 (`fc00::/7`) en `http:`. Ce que l’écart coûte : le code d’autorisation traverse le LAN en clair. Ce qui le rend tenable — et qui doit être reverifié avant d’y toucher — c’est le **cumul** de trois garde-fous, pas la confiance dans le réseau : PKCE **S256 obligatoire** (`app/oauth/authorize/route.ts:66`), donc un code intercepté est inexploitable sans le `code_verifier` qui ne transite jamais par la redirection ; code à **usage unique** (supprimé à l’échange, `app/oauth/token/route.ts:110`) ; **TTL 60 s** (`AUTHORIZATION_CODE_TTL_MS`). Relacher l’un des trois rouvre la question. Les bornes sont testees (`172.15`/`172.32` hors plage, IP publique en clair refusée) — l’écart n’est pas « on accepte http ». Non couvert volontairement : les noms mDNS `*.local`, dont rien ne permet de vérifier la résolution à l’enregistrement.

**`NextResponse.redirect()` vaut 307 par défaut, et 307 préserve la méthode — mortel pour une réponse OAuth qui suit un POST (issue #201)** — `app/oauth/authorize/route.ts` répond à la **soumission POST** du formulaire de consentement, puis redirige vers le `redirect_uri` du client. Or la réponse d’autorisation doit y arriver en **GET** (RFC 6749 §4.1.2, paramètres en query string). `NextResponse.redirect(url)` sans statut vaut **307** (`node_modules/next/dist/server/web/spec-extension/response.js:99`, `?? 307`), qui **conserve la méthode** : le navigateur re-POSTait donc sur le callback du client. Constaté le 2026-09-07 avec un vrai client MCP, dont le callback (FastAPI, déclaré en GET) répondait `{"detail":"Method Not Allowed"}` — échec survenant **après** le consentement, donc tout le handshake paraissait fonctionner jusqu’au dernier saut. Utiliser **303 See Other** (constante `SEE_OTHER`), le statut prévu pour « ce POST est traité, va chercher la suite en GET » ; ne jamais revenir à 307/308 ici. **Ce que trois niveaux de tests n’ont pas vu, et pourquoi** : l’e2e (`e2e/mcp-oauth.spec.ts`) capturait la redirection et n’en lisait que l’**URL** — un commentaire disait même « on n’a besoin que de l’URL » — or un 307 porte exactement la même URL, donc les trois tests passaient à l’identique ; et les tests unitaires ne sont pas passés à côté du bug, ils l’avaient **verrouillé** (`expect(response.status).toBe(307)`, comportement réel lu puis encodé sans se demander s’il était correct). Désormais `expect(redirectRequest.method()).toBe("GET")` accompagne chaque capture, et un test unitaire refuse explicitement 307/308 ; les deux ont été **prouvés sensibles** en repassant à 307 (`Expected: "GET" / Received: "POST"`). **Leçon transposable** : quand une redirection suit un POST, la propriété à asserter est la **méthode d’arrivée**, pas l’URL.

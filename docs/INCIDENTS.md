## Gemini Spark indisponible en EEE (issue #104)

**Vérification manuelle post-déploiement effectuée (issue #104) : Gemini Spark, hébergeant les « Custom apps », est indisponible en EEE — root cause côté Google, pas Dodojo** — les endpoints prod (`/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource`) répondent correctement (conformes RFC 8414/9728), l'implémentation Dodojo n'est pas en cause. Les hypothèses initiales de l'issue #104 (statut du consent screen Google Cloud, account-linking, scopes) visaient en réalité **Gemini Enterprise Agent Platform** (produit entreprise, IAM/OAuth client type Okta/Azure AD) — mécanisme sans rapport avec ce qui est implémenté ici. Le mécanisme grand public pertinent s'appelle **« Custom apps for Spark »** : l'utilisateur colle lui-même une URL de serveur MCP dans Gemini > Paramètres > Apps connectées — aucun listing, aucune vérification Google, aucun statut de consent screen à surveiller ; Dodojo ne « apparaîtrait » donc jamais spontanément dans une liste, la feature ne fonctionne pas ainsi. **Vérifié en direct sur un compte réel (Android, France)** : la section « Custom apps »/MCP n'existe pas du tout dans les réglages Gemini — seules des intégrations pré-construites (Spotify etc., partenariats Google directs, mécanisme totalement différent et sans rapport avec RFC 7591) y figurent. Cohérent avec le rollout du produit **Gemini Spark**, qui exclut aujourd'hui l'EEE/UK/Suisse/Nigeria (revue de conformité AI Act européen en cours, aucune date officielle ferme) — root cause de #104, indépendante de toute config Dodojo, rien à corriger côté code pour rendre la fonctionnalité disponible aujourd'hui. Issue laissée ouverte, à retester quand Google étendra Gemini Spark à l'EEE.

## Race condition sur l'ordre d'une fratrie (issue #195, avant correctif)

**L'ordre d'affichage d'une fratrie était DÉRIVÉ d'un calcul au clic, jamais écrit avant réponse serveur — race condition** — `Arena.handleToggle`/`handleAdd`/`handleAddSubtask` calculaient l'ordre cible d'une fratrie au moment du clic (`planCompletionReorder`/`insertNewActiveTaskId`) puis n'appelaient `reorderSiblings(parentId, orderedTaskIds)` qu'**après** la réponse de la mutation. Toute mutation concurrente pendant la fenêtre réseau rendait ce payload périmé, avec deux modes de défaillance **silencieux** : `reorderSiblings` rejette le payload **entier** si un seul id est devenu `is_abandoned` entre-temps (l'appel étant best-effort, aucun message — la tâche reste en place) ; sinon le serveur ne renumérote **que les ids reçus**, laissant les autres membres du groupe sur leur ancienne position → **positions dupliquées**, départagées arbitrairement par Postgres puisque le tri portait sur `position` seule. La sérialisation par fratrie (`reorderQueueRef`, issue #144) garantit l'ordre d'**application**, pas la **fraîcheur** des payloads — c'est pour ça qu'elle n'avait rien corrigé. Reproduit sous latence simulée (1,5s) en cochant deux tâches d'affilée : `0·A 1·B 2·C 3·D` → les deux complétées remontaient **en tête**. La fenêtre étant la latence réseau, le bug était fréquent en 4G et quasi introuvable en local. Dégâts mesurés en base avant correctif (données réelles) : 3 groupes à positions dupliquées (dont `[0,0,0,3,5]`) et 4 groupes violant l'invariant (dont `0· 1· 2✓ 3· 4·`).

**Piste abandonnée** : une première version du correctif renumérotait le groupe côté serveur (`normalizeSiblingPositions`, appelée par les 8 actions qui changent la composition d'un groupe) — fonctionnellement correcte, mais mesurée trop coûteuse : cocher la première tâche d'une liste de 20 décale les 20 lignes (20 `UPDATE` séquentiels), et une boucle qui coche tout devient quadratique (suite e2e complète ×2, 1,8→2,7min sur un seul spec).

**État actuel** : résolu par le correctif dérivé au rendu (`compareForDisplay`, `lib/game-engine.ts`) — voir l'entrée « L'ordre d'affichage d'une fratrie est DÉRIVÉ du contenu » dans `CLAUDE.md`.

## Runner CI ~1.5-2x plus lent que le poste local pour l'E2E (2026-08-02)

**Timeout par test recalibré** — Le job E2E n'ayant jamais tourné jusqu'au bout en CI avant le fix Node 20→24 (cf. entrée dédiée ci-dessous), aucun timeout Playwright n'avait jamais été validé contre le matériel réel du runner GitHub Actions. Découvert sur la PR #157 (issue #156) : deux runs CI consécutifs échouent **de façon déterministe** (pas un flake aléatoire — mêmes tests, 3 tentatives chacun avec les 2 retries CI) sur des attentes (`page.waitForLoadState("networkidle")`, `toBeEnabled({ timeout: 15_000 })`) qui passent en 15-20s en local, avec le run entier durant 16-19min en CI contre 9.5min en local pour la même suite de 52 tests. `playwright.config.ts` a fixé `timeout: process.env.CI ? 60_000 : 30_000` (le timeout par défaut de 30s ne suffisait pas). Si un nouveau timeout CI apparaît malgré cette marge doublée, vérifier d'abord si le run entier a ralenti encore (accumulation de données sur le compte e2e partagé, RG-04 interdisant tout DELETE) avant d'incriminer un test précis.

## Récit détaillé des trois timeouts Playwright et de l'échantillonnage d'animation (2026-08-03)

**Trois timeouts Playwright indépendants, et le plus lent des deux environnements n'est pas toujours la CI** — `playwright.config.ts` en porte trois qui ne se déduisent pas l'un de l'autre : `timeout` (budget par test), `expect.timeout` (par assertion) et `webServer.timeout` (démarrage du serveur). Ce dernier est passé de 240s à **600s**, **sans** variante `process.env.CI` — c'est un *plafond d'attente*, pas un délai payé : Playwright rend la main dès que `url` répond. Et contre-intuitivement le côté lent ici est le **poste local**, pas la CI : mesuré sur le run 30768754776, la CI met **29s** pour `prebuild` + `build` + `start` + `globalSetup` (le job `checks` construit en 17s), là où le même build dépasse 240s sur un poste Windows (antivirus + worktree avec son propre `node_modules`). **Cascade trompeuse du dépassement** : le `npm run build` tué à mi-parcours laisse `.next` incomplet, et c'est le run **suivant** qui échoue, sur « Could not find a production build in the '.next' directory » — un message qui accuse un build absent au lieu du timeout qui l'a interrompu. Les deux jobs de `ci.yml` portent par ailleurs un `timeout-minutes` (15 / 45, au lieu du défaut GitHub de 360) pour qu'un job bloqué ne puisse plus consommer les crédits Actions du repo.

**`expect.timeout` est un réglage DISTINCT de `timeout`** — Suite directe de l'entrée ci-dessus : après le passage à `timeout: 60_000`, il restait **un** échec CI déterministe (3 tentatives, signature identique) — `journey-full-day.spec.ts` sur `expect(recap).toBeVisible()`, `Timeout: 5000ms`. Cause : `timeout` est le budget **par test**, les assertions gardent le défaut Playwright de **5s** tant que `expect: { timeout }` n'est pas posé. Or cette assertion suit immédiatement `await closeDayAction()` et `closeDay` enchaîne ≥10 aller-retours Supabase séquentiels. **Mesuré, pas supposé** : le rapport Playwright du run 30768754776 (`gh run download <run> -n playwright-report`, `0-trace.network` du trace de retry) donne **5853ms** pour ce POST depuis un runner en région `iad` — 853ms de trop. Le snapshot `error-context.md` confirme visuellement : bouton HUD rendu `[disabled]`, server action encore en vol. `playwright.config.ts` pose donc `expect: { timeout: process.env.CI ? 15_000 : 5_000 }`.

**Assertions e2e sur un état d'animation transitoire — deux fausses pistes traversées** — `combat-animations.spec.ts` enchaînait `await expect(boss).toHaveAttribute("data-anim-state", "attack")` puis `hurt`. Le `hurt` ne dure que 350ms et ne démarre qu'à la frame d'impact de l'attaque du Boss (~40% d'une anim de 600-800ms). Le poll de `expect` recule (100ms→250→500→1000ms) : flake CI avec 14 résolutions consécutives à "idle", reproduit en local en mode CI avec 33 résolutions sur 15s. ⚠️ (1) Armer les deux `expect(...)` avant le déclencheur puis `Promise.all` — **empire** le problème : les polls commencent plus tôt, donc leur intervalle a déjà reculé à 500-1000ms quand la fenêtre arrive. (2) Un `MutationObserver` attaché aux deux nœuds `[data-testid="character-sprite"]` — **ne remonte rien du tout** : `Arena.tsx` re-keye le bloc contenant `VersusScene` (`key={pulse ? \`fx-${pulse.key}\` : "fx-idle"}`) et toute action qui change les HP change `pulse`, donc React **remonte la scène entière au moment même du déclencheur** ; les nœuds observés sont détachés et l'observateur devient orphelin. Symptôme trompeur : `{heroHurt: false, bossAttack: false}` — un faux négatif sur les DEUX personnages, lisible à tort comme « la contre-attaque n'a pas lieu ». Corollaire pour `ko-overlay-viewport.spec.ts` : le `guard < 20` d'origine était la vraie cause du flake — le compte e2e partagé dépasse depuis longtemps 20 entrées, donc la boucle rendait la main Boss debout et le test échouait sur l'absence d'overlay, symptôme sans rapport apparent avec la borne.

**État actuel** : la version compacte de ces trois règles (timeouts séparés, méthode `error-context.md`+trace, échantillonnage rAF plutôt que poll, sortie de boucle sur `aria-valuenow`) vit dans `CLAUDE.md`.

## CI figée sur Node 20 alors que les dépendances exigent Node ≥22 (2026-08-01)

**Désynchronisation silencieuse de `npm ci`** — `.github/workflows/ci.yml` pinnait `node-version: 20` pour les deux jobs (`checks`/`e2e`), rouge sur **tous** les runs `main` depuis le 2026-07-27 sans que personne ne le remarque (chaque run échoue en <20s, avant même lint/tests). Cause : `@supabase/*@2.110.7` et `@testing-library/jest-dom@7.0.0` déclarent désormais `engines.node >=22`, et `package-lock.json` est généré/committé depuis un poste local en Node 24/npm 11 — sous Node 20/npm 10.8.2 (runner CI), `npm ci` calcule un arbre idéal différent et rejette le lock en `EUSAGE` (« Missing: @swc/helpers@0.5.23 from lock file »), un message qui pointe vers un faux problème de lockfile alors que la cause réelle est l'écart de version Node/npm. Corrigé en alignant `node-version: 24` dans `ci.yml` et en ajoutant `engines.node: ">=22.0.0"` à `package.json`.

**Corollaire découvert en corrigeant ce point** : le job `E2E (Playwright)` n'avait *jamais* réellement exécuté un test depuis la mise en place des secrets (2026-07-20) — `needs: checks` le faisait sauter (`skipping`) à chaque fois que `checks` échouait avant lui, masquant une **cascade** de secrets jamais câblés dans `ci.yml` ni créés côté GitHub : `NEXT_PRIVATE_KEY_SUPABASE`, puis `E2E_ONBOARDING_EMAIL`/`E2E_ONBOARDING_PASSWORD`. Les trois sont désormais référencés dans `ci.yml` et renseignés (`gh secret set <NOM> --repo ouro84/dodojo`). Piège à surveiller : un job qui n'a jamais tourné jusqu'au bout peut masquer plusieurs gaps de config empilés — après en avoir corrigé un, ne pas supposer que le suivant est le dernier avant d'avoir vu le job passer entièrement au vert au moins une fois.

**État actuel** : la règle courte (« toujours vérifier la version Node du runner CI avant de suspecter le lockfile ») vit dans `CLAUDE.md`.
